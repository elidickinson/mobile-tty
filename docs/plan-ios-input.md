# Plan: iOS swipe/dictation input, and owning wterm/dom

Two bugs from on-device use, one decision about the dependency they live in.

## The bugs

- Words written with swipe typing (QuickPath) are inserted with no spaces between them.
- After swipe-typing, and after iOS dictation, the view is scrolled to the top of scrollback.

## Diagnosis

Both trace to `InputHandler` in `@wterm/dom` and where the app mounts it. The handler creates a hidden textarea styled `position: absolute; top: 0; left: -9999px` and appends it to the terminal element, which here is `#screen`, the scrollback scroller. `#screen` really is the containing block even though `#stage` is `position: relative`: wterm's own `terminal.css` declares `.wterm { position: relative }` and is bundled ahead of style.css, so `top: 0` is the top of scrolled content. Its input model is send-and-wipe: on every non-composing `input` event it sends the field's value and sets `value = ""`; on `compositionend` it sends `e.data` and wipes again. The field is empty at essentially all times. That emptiness is load-bearing for the iOS delete key: iOS natively edits the focused field despite keydown preventDefault, so an always-empty field is what keeps native deletion a no-op and backspace arriving only as clean keydowns. (It is also why the key bar's `⌫` implements its own repeat.)

**No spaces.** iOS inserts the separator space before a swiped word only when the field is non-empty at that moment, i.e. the previous word is still in it. Since wterm wipes the field after every commit, each swipe starts an empty field and inserts bare. Nothing is desynced; the separator simply is never due. No event carries "a space was owed", so this is unfixable at the app layer without changing the wipe behavior.

**Scroll to top.** Plain key taps are preventDefaulted at keydown, so no text ever lands in the DOM. Swipe and dictation perform real insertions into the field, after which WebKit reveals the caret/focused editable by scrolling it into view. The caret sits at the top of `#screen`'s content, so the reveal sets `scrollTop ≈ 0`. The app's own scroll machinery then faithfully preserves that imposed position.

Related actor: wterm calls `_scrollToBottom()` before forwarding every `onData`. Typing while parked in scrollback snaps to the bottom today, and swiped words will keep doing that once the reveal is fixed. Decision: accept it. It matches tapped-key behavior, and the reported bug is the jump to the top.

**A latent perf bug, found during review.** The app's `r.render` rebind (app.js, `r.render = core => ...`) drops the second argument that the 0.3.4 signature `render(core, viewport)` carries. Without a viewport, `syncScrollback` gets `rowHeight = 0`, its staleness short-circuit never runs, and every render builds row content for the entire scrollback -- up to 1000 rows per frame during streaming output. It also means the 0.3.3-era ring-freeze cannot manifest today, so any re-validation of the scrollback workaround is meaningless until the arity is restored.

## Decision: vendor @wterm/dom

The input fix rewrites `InputHandler`'s event wiring and DOM ownership. Doing that through runtime surgery in app.js (removing its listeners, wrapping private bound methods) is maintaining a fork with worse tooling. The surrounding inventory points the same way: the `_renderedScrollbackCount` workaround for the scrollback ring bug, the `r.render` / `_doRender` rebinds, a guard block that exists to throw when internals move, and known core bugs (column-shrink data loss; `research/ghostty-vt-core` evaluates a future core swap). The arity bug above is the pattern made real: a silent two-line drift with a per-frame cost, surviving only because nothing checked it.

Form: `git subtree` of the upstream TS repository, pinned to a recorded SHA, imported by path; drop the npm dependency. Not a copy of `dist` or TS reconstructed from sourcemaps -- the merge path is the point, so every upstream release can be a three-way merge. PRs go upstream in parallel, targeting upstream main (not the recorded SHA); if a release lands the fixes, retire the vendor. Going back to npm is a manual undo, not a revert -- acceptable, but write the steps down when the subtree lands.

Mechanics to handle in the transition: repoint `server/client.js` (it reads `node_modules/@wterm/dom/src/terminal.css` directly); add a `tsc --noEmit` script, since esbuild strips types without checking them and the repo has no tsconfig -- without it the vendored TS gets less checking than the npm package provides, which would undercut the rationale. Retire the app.js monkeypatches in the same move: the guard block and the `_renderedScrollbackCount` workaround die with the re-validation; the `_doRender` latch fix becomes an in-source edit. `terminalInput()` becomes `term.input.textarea` instead of a DOM query.

Scope: `@wterm/core` stays on npm, pinned exact. Its real defects live in the compiled Zig/WASM, which vendoring the JS shell does not touch, and the ghostty work is a future dependency swap, not a vendoring decision. Watch item once dom is vendored: dom/core API skew is ours to notice on every upstream merge.

One caution: the installed dom is 0.3.4, not the 0.3.3 the `eli/` notes describe (the lockfile had drifted to 0.3.3 while node_modules ran 0.3.4; package.json is now pinned exact). The 0.3.4 renderer rewrote scrollback rendering as a virtualized overscan window with spacers, keyed off `getScrollbackDiscardedCount()` -- the very API the eli writeup asked upstream for. The app's `rebuildScrollback`/`ringTurn` math assumes the old append model and must not be ported into the vendor without re-validation.

## Sequence

1. **On-device experiment (gates everything).** A plain page with a styled-hidden `<textarea autocapitalize="off" autocomplete="off" autocorrect="off" spellcheck="false">`. Three questions, one trip:
   - (a) Two consecutive swipes yield `hello world` when the field keeps the first word -- i.e. the separator really depends on a non-empty field. If this fails, the delta approach is dead and the plan is re-opened.
   - (b) What order do `compositionend` and the final `input` fire in, and does the final event carry the commit? The flush design below is ordering-proof, but the answer goes in the notes.
   - (c) A bottom-pinned field in a tall scroller does not get scrolled on swipe/dictation. This is the other unverified WebKit claim, and the placement fix below gates on it.
2. **Vendor 0.3.4** via git subtree. Restore the `render(core, viewport)` arity as part of retiring the app.js rebinds. Delete the internals guard block; switch imports to the path; repoint terminal.css; add `tsc --noEmit`.
3. **Scrollback re-validation.** Only after the arity fix: establish whether the ring-freeze still reproduces against the working virtualized renderer; expected answer is no, and `rebuildScrollback`/`ringTurn` are deleted outright. Measure per-frame scrollback cost before and after the arity fix. Note the e2e assumptions that virtualization invalidates: scroll-trace's DOM-index-to-core-offset mapping, scrolling.spec's "last scrollback row is the newest line" assertion, and the `domRows` diagnostics readout all assume a 1:1 DOM-row/core-line mapping that an overscan window removes.
4. **Input fix, in source.**
   - Delta-sync: the field keeps its content; `sent` mirrors what has been transmitted. On each relevant event, `flush()` runs a common-prefix/suffix diff between `sent` and the field, sends `'\x7f'.repeat(deleted) + inserted`, and updates `sent`. Callers: `compositionend` (clears the composing flag, then flushes) and non-composing `input`. The diff is idempotent -- a second flush with no change sends nothing -- so engine ordering (Firefox emits the final composing `input` before `compositionend`; Safari and Chrome after) cannot strand or duplicate a commit. `sent` still has exactly one writer.
   - Erase units: count `\x7f` repeats in whatever pi's line editor erases per DEL, determined empirically (code points vs graphemes differ for emoji ZWJ sequences), never UTF-16 units. Write the answer down. Translate `\n` to `\r` in inserted text (dictation can produce `insertParagraph`).
   - The mirror invariant: in delta-sync the field is a mirror of the PTY's input line, and any byte reaching the PTY from outside the diff invalidates it -- bar keys (`⌫`, arrows, Enter, Escape, Tab), hardware Enter and Backspace, paste, the menu's Send. Enter is the common case that corrupts: PTY consumes the line, the field still holds it, and the next swipe adds a leading space to a fresh prompt. Enforce it in one place: the app already funnels PTY writes through `conn.send`, so a write that did not come from the diff clears the field and `sent`. The diff path marks itself. Session boundaries (reconnect, snapshot delivery, folder switch, keyboard dismiss/blur) clear it too.
   - Backspace ownership: field empty, stock keydown path (preventDefault, send `\x7f`). Field non-empty, no preventDefault and no send; the native deletion arrives as `deleteContentBackward` and goes through the diff. The `if (composing) return` guard stays first in the keydown path.
   - Textarea placement: keep it inside the terminal element (the e2e suite selects `#screen textarea` in ~30 places) but `position: sticky` at the scroller's visible bottom edge, so caret reveal targets already-visible geometry. Sticky, not a derived `top` written from scroll handlers -- the reveal happens synchronously with insertion and a stale write on iOS mid-momentum reintroduces the jump intermittently. Sticky is in-flow: give the field `height: 0` so it adds nothing to `scrollHeight` (`sizeScreen` maintains a whole-rows box, and a non-multiple breaks wterm's 5px follow-output tolerance), and confirm on-device that a zero-height field still takes focus and the keyboard. Keep it offscreen horizontally (`left: -9999px`) so letterboxing never shows it.
   - Hygiene: the mirror invariant covers the corruption cases; the remaining rule is size -- clear the field and `sent` when not composing past ~4KB, so an all-day dictation session does not grow an unbounded buffer.
   - Noted, not fixed: one-character deltas (a lone `\x7f`, a one-letter word) are length 1 and will consume armed sticky modifiers via `withMods`, same as single keystrokes today. Intentional; do not rediscover it as a bug.
5. **Upstream PRs** against upstream main: the input delta model, the arity/viewport handling, and the scrollback findings. Retire the vendor when they land.
6. **Accepted behaviors, documented:** swiping while parked in scrollback snaps to the bottom, consistent with tapped keys (the wterm data-path `_scrollToBottom()` stays).

## Verification

Unit tests for the diff: insert, delete, replace, ambiguous overlap where prefix and suffix compete, emoji insert-then-delete, `\n` handling, and flush idempotence. On-device checklist: two swipes produce a space; swipe then immediate software `⌫` is a single delete with no junk; swipe, then Enter, then swipe -- the new burst starts clean, no leading space; bar-`⌫` then swipe -- the mirror invariant holds (no ghost characters); dictation while scrolled into history does not jump; a zero-height sticky field opens the keyboard; holding software `⌫` with field content repeats natively with a correct count; `⌫` on an empty field still deletes; reconnect mid-burst leaves no stale mirror; keyboard open/close has no new wobble; `⌘`/desktop IME and hardware backspace remain sane, including CJK commit; e2e suite green (scrollback-assumption tests updated per step 3, selectors untouched).
