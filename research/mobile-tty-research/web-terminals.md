# Research: web terminals

## xterm.js surface and addons
- xterm.js describes itself as a browser frontend rather than a shell or server; the embedding application connects `Terminal.onData`/`Terminal.write` to a PTY transport. Its maintained addons include attach, clipboard, fit, image, ligatures, progress, search, serialize, Unicode graphemes, Unicode 11, web fonts, web links, and WebGL [source](https://github.com/xtermjs/xterm.js).
- The Unicode 11 addon installs Unicode 11 character-width rules and requires explicitly setting `terminal.unicode.activeVersion = '11'` after loading it [source](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-unicode11/README.md).
- The image addon supports SIXEL, iTerm inline images, and partial Kitty graphics; it documents configurable pixel/payload/storage limits and potentially large JavaScript memory use [source](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-image/README.md).
- xterm.js input writes are queued and parsed in event-loop slices intended to stay below one frame. Its flow-control guide reports roughly 5–35 MB/s processing and a hard write-buffer limit, and shows high/low-watermark pause/resume messages spanning WebSocket and PTY layers [source](https://xtermjs.org/docs/guides/flowcontrol/).

## Search in scrollback
- `@xterm/addon-search` exposes `findNext` and `findPrevious` over the terminal buffer [source](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-search/README.md).
- Search options include regex, whole-word, case sensitivity, decorations, and `incremental`. The documented meaning of `incremental` is that `findNext` can expand the existing selection while it continues to match text being typed; it does not apply to `findPrevious` [source](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-search/typings/addon-search.d.ts).
- Decorations can distinguish all matches from the active match with background/border colors and overview-ruler colors. `onDidChangeResults` reports active result index and result count; the index becomes `-1` when the highlight threshold is exceeded [source](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-search/typings/addon-search.d.ts).
- The current addon defaults to at most 1,000 highlighted matches. A search with decorations scans from the start, records matches until the limit, registers decorations, selects the active match, and scrolls an offscreen result toward the middle of the viewport. Buffer writes and resizes trigger a 200 ms delayed match update [source](https://raw.githubusercontent.com/xtermjs/xterm.js/master/addons/addon-search/src/SearchAddon.ts).
- An xterm.js performance report found that increasing highlights from 1,000 toward Monaco’s 20,000 could block rendering. In one test, locating 72,960 matches directly took about 46–100 ms, while the then-current full addon path took about 6.3 seconds; marker/decoration creation and disposal were major measured costs [source](https://github.com/xtermjs/xterm.js/issues/5176).
- The same performance thread reports an experiment that returned a small result set, yielded to the main thread, and then completed the result set, which improved perceived UX; another proposed pattern was to decorate visible rows first and process the rest in later chunks [source](https://github.com/xtermjs/xterm.js/issues/5176#issuecomment-2563395791).
- VS Code’s integrated-terminal UX opens Find with Ctrl/Cmd+F and highlights all text matching the query [source](https://code.visualstudio.com/docs/terminal/basics#_find).
- UNCERTAIN: The API calls its selection-preserving behavior “incremental” [source](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-search/typings/addon-search.d.ts), while the search performance issue says successive searches still rescan and are “not incremental” in the sense of narrowing cached results [source](https://github.com/xtermjs/xterm.js/issues/5176). These sources use “incremental” for different behavior.

## Tappable URL detection
- xterm.js supports explicit OSC 8 links in core and implicit HTTP/HTTPS URL detection through the web-links addon [source](https://xtermjs.org/docs/guides/link-handling/).
- The web-links addon’s default regular expression begins at `http://` or `https://`, excludes whitespace, quotes, unsafe punctuation, and dangling terminal punctuation, and validates each regex match with the browser `URL` constructor [source](https://raw.githubusercontent.com/xtermjs/xterm.js/master/addons/addon-web-links/src/WebLinksAddon.ts).
- Detection is computed for a requested buffer row. The provider joins wrapped lines above and below the row, stopping at whitespace or 2,048 characters, then maps JavaScript string offsets back to terminal cells, including corrections for wide characters across wraps [source](https://raw.githubusercontent.com/xtermjs/xterm.js/master/addons/addon-web-links/src/WebLinkProvider.ts).
- The default activation opens a new window, clears `window.opener`, and then navigates it to the URI; custom activation, hover, leave, and URL-regex behavior can be supplied [source](https://raw.githubusercontent.com/xtermjs/xterm.js/master/addons/addon-web-links/src/WebLinksAddon.ts).
- xterm.js’s link guide shows a Ctrl/Cmd-click gate to prevent accidental activation and a hover popup that reveals the complete URL, particularly for OSC 8 links whose displayed label can differ from the destination [source](https://xtermjs.org/docs/guides/link-handling/).
- VS Code layers URI, verified file, folder, and workspace-word link providers over xterm.js. Its “Open Detected Link” command presents all links in the viewport in a searchable keyboard-accessible picker, avoiding pointer-only activation [source](https://code.visualstudio.com/docs/terminal/basics#_links).
- UNCERTAIN: The addon API and implementation describe activation with `MouseEvent`, hover, and leave [source](https://raw.githubusercontent.com/xtermjs/xterm.js/master/addons/addon-web-links/src/WebLinkProvider.ts); no addon documentation found in this research specifies tap, long-press, or modifier behavior on iPhone.

## Clipboard and mobile Safari
- xterm.js core leaves ordinary copy/paste policy to the embedding application because Ctrl+C and Ctrl+V are terminal input. A maintainer recommends `attachCustomKeyEventHandler` to intercept selected shortcuts and let the browser’s copy/paste events proceed [source](https://github.com/xtermjs/xterm.js/issues/2478#issuecomment-543246347).
- `@xterm/addon-clipboard` implements OSC 52 clipboard reads and writes. Its default browser provider directly calls `navigator.clipboard.readText()` and `writeText()`; it does not include an `execCommand` fallback [source](https://raw.githubusercontent.com/xtermjs/xterm.js/master/addons/addon-clipboard/src/ClipboardAddon.ts).
- The Clipboard API is restricted to secure contexts. MDN reports that Safari requires transient user activation for writes and, for reads not otherwise allowed, presents an ephemeral Paste UI; Safari does not support persistent `clipboard-read` or `clipboard-write` Permissions API grants [source](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API).
- WebKit documents that Safari 13.1 added async clipboard support. On iOS, a programmatic read outside permitted conditions can present a one-item paste callout; tapping elsewhere, switching tabs, or hiding Safari rejects the request. Writes and reads must originate within a user gesture unless same-origin clipboard rules apply [source](https://webkit.org/blog/10855/async-clipboard-api/).
- WebKit’s older copy pattern creates an invisible fixed input, focuses and selects its contents, and invokes `document.execCommand('Copy')`; the async API replaces that multi-step pattern with `navigator.clipboard.writeText` [source](https://webkit.org/blog/10855/async-clipboard-api/).
- MDN marks `document.execCommand()` deprecated and non-standard, recommends the Clipboard API, and notes that browser-specific conditions control whether its `copy` command is enabled [source](https://developer.mozilla.org/en-US/docs/Web/API/Document/execCommand).
- ttyd’s bundled xterm client auto-copies every nonempty terminal selection using `document.execCommand('copy')` and briefly shows a scissors overlay [source](https://raw.githubusercontent.com/tsl0922/ttyd/main/html/src/components/terminal/xterm/index.ts).
- Azure Cloud Shell assigns Ctrl+C to copy only when terminal text is selected; with no selection it sends Ctrl-C to the shell. Its documented paste alternatives include Ctrl+V and Shift+Insert [source](https://learn.microsoft.com/en-us/azure/cloud-shell/use-the-shell-window).
- Google Cloud Shell documents normal browser selection plus Ctrl/Cmd+C and Ctrl/Cmd+V, and also has a toolbar action for sending key combinations [source](https://docs.cloud.google.com/shell/docs/use-cloud-shell-terminal).
- Termius on iOS uses native selection handles and the native Copy/Paste context menu; it also documents three-finger paste and copying or sharing a file/image so it can upload through SFTP and insert the resulting remote path [source](https://docs.termius.com/terminal/mobile-terminal).

## DOM, Canvas, and WebGL rendering
- When xterm.js introduced its Canvas renderer, the project said measured performance benefits outweighed what it could achieve in DOM. It also listed lost DOM behavior—native text/node facilities and naturally represented links—and said page zoom could blur Canvas text [source](https://github.com/xtermjs/xterm.js/issues/935).
- xterm.js later made DOM the core default and moved Canvas to an addon to avoid loading unused code. The issue described DOM as smaller and adequate for casual integrations but “much slower” than Canvas on Safari/iPad at that time [source](https://github.com/xtermjs/xterm.js/issues/3271).
- In 2024, xterm.js removed the Canvas addon for the next major release after Safari/WebKit gained WebGL2 and DOM renderer performance work landed [source](https://github.com/xtermjs/xterm.js/issues/4779).
- In that removal discussion, a maintainer said the current DOM renderer only considers the visible viewport, so 0 and 100,000 rows of scrollback should have similar render cost unless screen-reader mode is enabled [source](https://github.com/xtermjs/xterm.js/issues/4779#issuecomment-2230507890).
- The same discussion reports full-viewport DOM rendering as reasonable for most uses after optimization, while WebGL retains lower render/input latency and custom glyphs. It also records concerns about WebGL context limits/loss and the documented response of disposing the renderer without losing terminal data or the connection [source](https://github.com/xtermjs/xterm.js/issues/4779#issuecomment-2231671142).
- The WebGL addon explicitly warns that browsers can drop contexts after OOM or suspension and exposes `onContextLoss`; its example disposes the addon to return to the default renderer [source](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-webgl/README.md).
- A Canvas issue describes Canvas 2D as synchronous and CPU-bound, drawing cached character bitmaps one by one. At thousands of columns it became unusable in reported Safari tests, while WebGL remained fast but exhibited texture stretching at extreme widths [source](https://github.com/xtermjs/xterm.js/issues/4175).
- UNCERTAIN: Historical xterm.js material describes DOM as much slower than Canvas on Safari/iPad [source](https://github.com/xtermjs/xterm.js/issues/3271), while the later Canvas-removal discussion says the optimized DOM renderer is now fast enough for most uses and can outperform Canvas on CPU-bound setups [source](https://github.com/xtermjs/xterm.js/issues/4779). The claims refer to different renderer generations.

## Resize and SIGWINCH
- The Fit addon computes columns and rows by reading the parent’s computed width/height, subtracting terminal padding and scrollbar width, and flooring by the renderer’s CSS cell dimensions. It enforces at least 2 columns and 1 row, and `fit()` calls `terminal.resize()` [source](https://raw.githubusercontent.com/xtermjs/xterm.js/master/addons/addon-fit/src/FitAddon.ts).
- Fit only changes the browser terminal’s dimensions. An xterm.js issue was resolved by forwarding `terminal.onResize({cols, rows})` to the backend and invoking the PTY’s resize method; without that propagation, tmux and Vim did not receive the changed size [source](https://github.com/xtermjs/xterm.js/issues/3873).
- ttyd listens for xterm’s resize event, sends a binary command containing JSON `{columns, rows}`, parses it server-side, and calls `ioctl(pty, TIOCSWINSZ, &winsize)` on Unix or `ResizePseudoConsole` on Windows [client source](https://raw.githubusercontent.com/tsl0922/ttyd/main/html/src/components/terminal/xterm/index.ts) [server source](https://raw.githubusercontent.com/tsl0922/ttyd/main/src/pty.c).
- ttyd’s stock client runs Fit on every `window.resize`; WeTTY likewise calls `fitAddon.fit()`, refreshes the rows, and emits `{cols, rows}` to its Socket.IO server when the window resizes [ttyd source](https://raw.githubusercontent.com/tsl0922/ttyd/main/html/src/components/terminal/xterm/index.ts) [WeTTY source](https://raw.githubusercontent.com/butlerx/wetty/main/src/client/wetty/term.ts).
- An Android Chrome report shows a Fit/PTY resize integration appearing visually wrong while continuous output was running and correcting after a keypress; the issue was closed without comments or a recorded resolution [source](https://github.com/xtermjs/xterm.js/issues/4744).
- No project named `DebouncedFitAddon` was found in xterm.js documentation or source during this research. The official Fit addon itself contains no debounce or resize observer [source](https://raw.githubusercontent.com/xtermjs/xterm.js/master/addons/addon-fit/src/FitAddon.ts).

## Reconnect, keepalive, resume, and repaint
- ttyd’s server has a configurable WebSocket ping interval (`--ping-interval`, default 5 seconds). Its libwebsockets policy uses the configured interval for a valid ping and treats the connection as hung 7 seconds later [manual](https://github.com/tsl0922/ttyd/blob/main/man/ttyd.man.md) [source](https://raw.githubusercontent.com/tsl0922/ttyd/main/src/server.c).
- ttyd’s bundled client refreshes `/token` before reconnecting. On a non-normal close it displays “Reconnecting…” and reconnects immediately; for a normal close it displays “Press Enter to Reconnect.” On successful reconnection it calls `terminal.reset()`, reenables input, and displays “Reconnected” [source](https://raw.githubusercontent.com/tsl0922/ttyd/main/html/src/components/terminal/xterm/index.ts).
- The stock ttyd client sets its reconnect flag false on the WebSocket `error` event; the close handler only auto-reconnects when its reconnect flags remain true [source](https://raw.githubusercontent.com/tsl0922/ttyd/main/html/src/components/terminal/xterm/index.ts).
- ttyd’s server starts one command/PTY for each WebSocket and sends the configured signal to that process when the WebSocket closes. Session continuity therefore comes from wrapping the command in tmux/dtach/screen rather than from ttyd replaying the old PTY [source](https://raw.githubusercontent.com/tsl0922/ttyd/main/src/protocol.c).
- GoTTY exposes `--reconnect` and a fixed `--reconnect-time` defaulting to 10 seconds. Its README recommends tmux or GNU Screen for sharing or preserving a process rather than claiming transport-level session replay [source](https://github.com/yudai/gotty).
- sshx advertises automatic reconnection, real-time latency estimates, and predictive local echo “à la Mosh,” alongside encrypted collaborative sessions [source](https://github.com/ekzhang/sshx).
- VS Code distinguishes process reconnection—reattaching to the same process after a window reload and restoring content—from process revive—relaunching after application restart and restoring serialized terminal content. Restored scrollback is configurable [source](https://code.visualstudio.com/docs/terminal/advanced#_persistent-sessions).
- VS Code also documents latency-triggered local echo: unconfirmed typed characters are displayed dimly, with dynamic exclusions for programs such as Vim, Nano, and tmux [source](https://code.visualstudio.com/docs/terminal/advanced#_reducing-remote-input-latency-preview).
- code-server retains disconnected clients for a configurable reconnection grace period, defaulting to 10,800 seconds (3 hours), after which the page must reload. It also writes a heartbeat file once per minute while a browser connection is active [source](https://coder.com/docs/code-server/FAQ#how-do-i-change-the-reconnection-grace-time).
- The experimental xterm serialize addon emits VT sequences that can be written into another same-sized terminal to restore rows, cursor, modes, alternate buffer, and optional scrollback; it can also serialize styled HTML [source](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-serialize/typings/addon-serialize.d.ts).
- xterm.js’s README describes a headless-terminal use case in which the server tracks terminal state and uses serialization so a frontend can restore state after reconnection [source](https://github.com/xtermjs/xterm.js).

## ttyd authentication, transport, and cheap server features
- ttyd supports Basic authentication (`--credential USER[:PASSWORD]`), reverse-proxy authentication by requiring a named header (`--auth-header`), TLS, and optional client-certificate verification through a CA file [source](https://github.com/tsl0922/ttyd/blob/main/man/ttyd.man.md).
- ttyd stores Basic credentials as base64 and serves that same encoded value from `/token` after applying the HTTP authentication check. The client sends it as `AuthToken` in the first WebSocket message, and the WebSocket server compares it with the stored value [HTTP source](https://raw.githubusercontent.com/tsl0922/ttyd/main/src/http.c) [protocol source](https://raw.githubusercontent.com/tsl0922/ttyd/main/src/protocol.c).
- The reverse-proxy auth mode checks that the configured header exists and copies its value to `TTYD_USER`; the source does not validate that value itself [source](https://raw.githubusercontent.com/tsl0922/ttyd/main/src/protocol.c).
- `--index` serves the supplied file as the index document. ttyd still reserves `/token` and `/ws`; other HTTP paths return 404. `--base-path` prefixes the index, token, and WebSocket endpoints for reverse-proxy mounting [source](https://raw.githubusercontent.com/tsl0922/ttyd/main/src/http.c).
- Other server controls include same-origin WebSocket checking, readonly-by-default operation with explicit `--writable`, maximum clients, one-client mode, exit when all clients disconnect, a Unix-domain-socket listener and owner, UID/GID/cwd selection, terminal type, IPv6, custom close signal, and URL-provided command arguments [source](https://github.com/tsl0922/ttyd/blob/main/man/ttyd.man.md).
- ttyd client options include disabling reconnect/leave warning/resize overlay, renderer type, font and arbitrary xterm options, Unicode 11, SIXEL, ZMODEM, trzsz, fixed title, and closing the browser window on disconnect [source](https://github.com/tsl0922/ttyd/blob/main/man/ttyd.man.md).
- ttyd’s bundled client includes high/low-watermark flow-control messages that pause and resume server-side PTY reads when browser terminal writes accumulate [client source](https://raw.githubusercontent.com/tsl0922/ttyd/main/html/src/components/terminal/xterm/index.ts) [server source](https://raw.githubusercontent.com/tsl0922/ttyd/main/src/protocol.c).

## Other browser terminal servers
- WeTTY runs xterm.js over WebSockets and can launch local login or SSH. It exposes SSH host/port/user/auth/key/config options, TLS certificates, base paths, iframe policy, and optional URL-selected remote hosts/commands [source](https://github.com/butlerx/wetty).
- WeTTY detects mobile user agents and skips WebGL on mobile. Its current client includes optional onscreen Ctrl, Esc, Tab, and arrow controls; resize fits locally, refreshes the viewport, and sends PTY dimensions [source](https://raw.githubusercontent.com/butlerx/wetty/main/src/client/wetty/term.ts).
- GoTTY is readonly except for resizing by default; options add writes, Basic auth, random URL, TLS, client certificates, custom index, reconnect interval, connection limits, and static or dynamic PTY dimensions [source](https://github.com/yudai/gotty).
- tty-share lets a participant join from either a browser or another terminal, supports readonly sessions and SSH-like TCP forwarding, and can use a hosted or self-hosted proxy. Its README says transport uses TLS/HTTPS but end-to-end encryption remains a TODO [source](https://github.com/elisescu/tty-share).
- sshx provides multiple movable/resizable terminals on an infinite zoom/pan canvas, live collaborator cursors, nearest-server routing, Argon2/AES end-to-end encryption, reconnect, latency estimates, and predictive echo [source](https://github.com/ekzhang/sshx).
- Shell In A Box implements its own browser terminal emulator and embedded web server, exporting arbitrary command-line tools to JavaScript/CSS browsers without plugins; it supports SSL when OpenSSL is installed [source](https://github.com/shellinabox/shellinabox).

## code-server and OpenVSCode Server
- OpenVSCode Server exposes upstream VS Code in a browser and uses connection tokens or token files for access; the project states that its changes are limited to the server scenario [source](https://github.com/gitpod-io/openvscode-server).
- code-server adds password authentication, sub-path hosting, self-contained webviews, a remote-port proxy, and self-hosted extension-gallery choices to browser VS Code [source](https://coder.com/docs/code-server/FAQ#whats-the-difference-between-code-server-and-openvscode-server).
- code-server recommends installing its iPad PWA for more screen space and top-level keyboard shortcuts. Its iPad documentation lists keyboard disappearance/focus issues, terminal copy/paste problems, terminal text not appearing, missing Escape on Magic Keyboard, and Ctrl+C not stopping a process; the documented Ctrl+C workaround sends `\u0003` through a terminal-focused keybinding [source](https://coder.com/docs/code-server/ipad).
- A code-server iPad trackpad issue reports that VS Code manually handles scrolling with `wheel` and `touchmove`, while the affected Safari version emitted `pointermove` without usable scroll deltas. Touch scrolling worked but initially lacked momentum [source](https://github.com/coder/code-server/issues/1455#issuecomment-610016124).

## Cloud Shell web clients
- Google Cloud Shell supports multiple terminal tabs connected to the same VM, keyboard and pointer scrollback, copy/paste, a Send Key Combination toolbar action, themes/fonts, scrollbar settings, AltGr mapping, and “Alt is meta” [source](https://docs.cloud.google.com/shell/docs/use-cloud-shell-terminal).
- Azure Cloud Shell supports multiple independent shell processes in browser tabs attached to one container, font/theme settings, file upload/download/drag-and-drop, web port preview, a browser editor, and opening the same container in VS Code for the Web [source](https://learn.microsoft.com/en-us/azure/cloud-shell/use-the-shell-window).
- Azure Cloud Shell keeps the session running while its portal pane is minimized, terminates it when closed, and terminates after 20 minutes without interaction [source](https://learn.microsoft.com/en-us/azure/cloud-shell/use-the-shell-window).

## Termius mobile and web availability
- Termius’s iOS terminal documents long-press-and-drag or Space-drag arrow gestures with repeat speed, double-tap Tab, pinch text scaling, native copy/paste, volume-button bindings, customizable groups of terminal keys above the system keyboard, snippets, command history, themes, voice typing, and SFTP-backed image/file paste [source](https://docs.termius.com/terminal/mobile-terminal).
- UNCERTAIN: Official Termius product and quick-start pages found in this research list macOS, Windows, Linux, iOS, and Android clients, but not a browser client [source](https://termius.com/index.html) [source](https://docs.termius.com/getting-started/quickstart). Search results for “Termius web” also returned an unrelated project spelled “Terminus Web”; no official Termius browser terminal was found.

## Mobile keyboard, viewport, and touch issues
- The Visual Viewport API distinguishes the layout viewport from what is visible. MDN explicitly notes that an on-screen keyboard can shrink the visual viewport without affecting the layout viewport; `height`, `offsetTop`, `resize`, and `scroll` are exposed to place UI in the visible region [source](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport).
- xterm.js’s broad mobile-support issue began with iPad Smart Keyboard arrows not reliably producing events while the hidden textarea was focused. It was closed after a maintainer said specific remaining mobile problems should get separate issues, but later Android comments still reported predictive-input problems [source](https://github.com/xtermjs/xterm.js/issues/1101).
- A predictive-keyboard issue reports Chrome Android retaining composition history, delayed predictive text, and counterintuitive backspace. A password input suppressed prediction in tests on Android, iOS, and macOS, but maintainers rejected it as confusing to screen readers and discussed input events and HTML attributes instead [source](https://github.com/xtermjs/xterm.js/issues/2403).
- An iPad ttyd report shows the software keyboard covering the bottom prompt with no way to scroll it above the keyboard; xterm.js closed the request for extra blank lines as part of its general mobile-support issue [source](https://github.com/xtermjs/xterm.js/issues/2672).
- xterm.js issue #1007 documents the conflict between native scrollback touch scrolling and translating a swipe to terminal arrows/mouse-wheel input for full-screen applications. One implementation watched terminal mode escape sequences and assigned swipe regions to arrows and scrolling [source](https://github.com/xtermjs/xterm.js/issues/1007).
- A hardware-keyboard issue reports Safari on iPhone/iPad/Vision Pro producing Enter (`keyCode 13`) for Ctrl+C, preventing SIGINT in terminal applications; it was associated with a milestone fix after xterm.js 6.0 [source](https://github.com/xtermjs/xterm.js/issues/5721).
- WeTTY’s mobile-key issue records smartphone users requesting optional Ctrl, Tab, Esc, and arrow buttons; the implementation is visible in the current client source [issue](https://github.com/butlerx/wetty/issues/557) [source](https://raw.githubusercontent.com/butlerx/wetty/main/src/client/wetty/term.ts).
