# Research: session persistence

Angle: session persistence, multiplexers, and reconnection tools — Mosh, Eternal Terminal, tmux -CC control mode, WezTerm multiplexer, abduco, dtach (features, forks like dtach-rev/dtach-plus), screen, Tabby, and "replay scrollback on reconnect" mechanisms. Heavy focus on Mosh's state-sync and tmux control mode (the two main "replay on reconnect" designs), plus real-world mobile/phone network reliability.

Context that motivated this: mobile-tty is a single-HTML TUI mobile web terminal served by ttyd, holding its session with `dtach -A -r winch -z pi`. dtach has no replay buffer, so on reconnect the client sends a resize nudge (N-1 then N, 120ms gap) to force a full repaint. This research covers how other tools solve (or fail to solve) that same "replay the screen on reconnect" problem.

## Mosh: State Synchronization Protocol (SSP) — the "replay" design

- Mosh is a remote terminal app providing "roaming," support for "intermittent connectivity," and "intelligent local echo and line editing." Both server and client each maintain a snapshot of the current screen state; the problem becomes state-synchronization ("fast-forwarding the client to the most recent screen") rather than sending a byte stream. [mosh.org](https://mosh.org/)
- This is the key replay-on-reconnect design: "With Mosh, the server runs a terminal emulator, and the server and client each maintain a snapshot of the current screen state." The client always gets brought up to the latest server screen state by diffing (skipping intermediate frames if needed). [Winstein & Balakrishnan, "Mosh: A State-of-the-Art Good Old-Fashioned Mobile Shell", USENIX ;login:](https://www.usenix.org/system/files/login/articles/winstein.pdf)
- SSP runs over UDP and "synchronizes the state of any object from one host to another." Datagrams are encrypted/authenticated with AES-128 in OCB3 mode. Mosh runs **two** copies of SSP, one each direction: client→server syncs the user's typed keystrokes (TCP-like semantics); server→client syncs an object representing "the current screen state," whose goal "is always to convey the client to the most recent server-side state, possibly skipping intermediate frames." [mosh.org](https://mosh.org/)
- Because SSP works at the object layer and controls the frame rate, it does not need to send every byte; Mosh regulates frames so as not to fill network buffers, and sets the min time between frames to half the smoothed RTT of the path. This is why Control-C stays responsive on bad links. [mosh.org](https://mosh.org/) / [;login: essay](https://www.usenix.org/system/files/login/articles/winstein.pdf)
- **How the diff/reconnect actually works** (per Keith Winstein, SSP author, in issue #1087):
  - "The sender always sends diffs. There is no 'full update' instruction."
  - A diff has three key fields: *source*, *target*, and *throwaway number*. Target is always the current sender-side state. Throwaway number is the most recent state explicitly acknowledged by the receiver. Source is either the most recent acknowledged state (guaranteed usable) OR a more recent state the sender *hopes* the receiver has (e.g. the target of the last transmitted diff).
  - On receiving a diff, the receiver throws away anything older than the throwaway number and tries to apply the diff; if it has the source state and the target is newer than its current state, it succeeds and acks the new target; otherwise it fails and just acks its current state number.
  - "Prophylactic retransmission" (p-retransmission): if a diff from a newer source state might get lost, the sender may instead send a diff from the last *explicitly acknowledged* state so it is guaranteed applicable, paying only slightly larger size when the diffs are similar size. [mobile-shell/mosh issue #1087 comment by keithw](https://github.com/mobile-shell/mosh/issues/1087)
  - "each message executes a transition from one state of the terminal (text presented on the screen, mostly) to another... basically streams of text/ANSI console commands... each message is a minimal repaint of the screen to a view at a later time." (cgull, maintainer comment) [issue #1087](https://github.com/mobile-shell/mosh/issues/1087)
- **Roaming** is stateless and needs no reconnect handshake: "Every time the server receives an authentic datagram from the client with a sequence number greater than any before, it sets the packet's source IP address and UDP port number as its new target." This works even when the client is behind a NAT that changed its public IP (e.g. tethering to a smartphone). Client sends a "heartbeat" at least every three seconds. Roaming works whether or not the client knows its IP changed. [mosh.org](https://mosh.org/) / [;login: essay](https://www.usenix.org/system/files/login/articles/winstein.pdf)
- **Predictive local echo**: the client runs a background predictive model hypothesizing each keystroke echoes at the cursor and that backspace/left/right arrows have traditional effect. Predictions are done in "epochs" — predictions start in the background, and only once one prediction in an epoch is confirmed by the server are the epoch's predictions shown to the user (and futures in the same epoch). Uncertain predictions are underlined (drawn as trailing underlines) until the next server state confirms/corrects them. By default predictions appear only on high-delay links or during network "glitches." [mosh.org](https://mosh.org/)
- **Relevant cost of prediction for TUIs / pi.dev**: "Mosh's predictive local echo... does not work well for anything that doesn't use line input (like vi command mode) as it would echo all your typed characters first on the screen and then the server would correct it." A commenter using irssi with `--predict=experimental` warns it echoes typed characters first and then rectifies; also briefly reveals password characters. So predictive echo is risky for a modal TUI (pi.dev alternates modes, uses arrows a lot). [LWN comments — hifi](https://lwn.net/Articles/722923)
- Mosh "is not an SSH replacement": still needs SSH to bootstrap (`mosh-server` started via SSH, then SSH connection closed); does not do port forwarding, X11, or ssh-agent forwarding. [LWN "Entering the mosh pit"](https://lwn.net/Articles/722923)
- **Scrollback limitation (important)**: Mosh "synchronizes only the visible state of the terminal." "no guarantee that the user will be able to scroll back to history that was missed." The workaround is tmux or screen on the server side. This is the [famous issue #2](https://github.com/mobile-shell/mosh/issues/2). [mosh.org FAQ](https://mosh.org/) / [;login: essay](https://www.usenix.org/system/files/login/articles/winstein.pdf)
- **No reconnect after client reboot/room-change**: "Mosh doesn't support... reattaching if the client has rebooted or the user has moved to a different machine." The mosh server has a single session; a fresh client cannot attach to an existing running mosh session. Users pair mosh with tmux/screen when they need real persistence across client restarts — a commenter describes: create a new mosh session, kill the old mosh server, attach tmux again. [;login: essay](https://www.usenix.org/system/files/login/articles/winstein.pdf) / [LWN comment — falstaff](https://lwn.net/Articles/722923)
- Mosh has no root, no daemon, no listening port (runs as a normal user, binds a high UDP port in 60000–61000). [mosh.org](https://mosh.org/)
- Desktop sleep/resume works: "you can put your laptop to sleep and wake it up later, keeping your connection intact." (two-way with dtach-style session hold). [mosh.org](https://mosh.org/)
- Server can auto-terminate dormant sessions via `MOSH_SERVER_NETWORK_TMOUT` / `MOSH_SERVER_SIGNAL_TMOUT`. [mosh.org FAQ](https://mosh.org/)
- Real-world: Mosh reduced median keystroke response from 503ms to near-instant (over 3G, ~half-second RTT); mean from 515ms to 173ms. [mosh.org](https://mosh.org/)
- Mobile clients exist: Blink Shell (iOS), JuiceSSH + Termux (Android). Mosh 1.4.0 (Oct 2022) added true-color support. [mosh.org](https://mosh.org/)
- UNCERTAIN: Whether mosh-server+mosh-client can reconnect to an *existing* long-lived session after the client briefly loses connectivity vs. after the client process exits entirely. Sources agree on roaming/sleep recovery being seamless (same client process), but a commenter reports "if the client goes down (laptop reboot) you cannot reconnect to the server" — the session's only keepalive is via UDP heartbeats and there's an inactivity TMOUT. [LWN comment — rsidd](https://lwn.net/Articles/722923) and [;login: essay limitation list](https://www.usenix.org/system/files/login/articles/winstein.pdf)
- UNCERTAIN: SSP standardization feasibility — requested as an IETF draft in #1087; maintainer cgull declined: "SSP is not at all extensible, and it is strongly tied to the Mosh codebase." Alternative clients (e.g. PuTTY) would need protocol documentation that does not really exist yet. [issue #1087](https://github.com/mobile-shell/mosh/issues/1087)
- Design lesson noted by maintainer: same sender/receiver diff-ack window (like TCP seq/ack) is used so the server never needs a "full state" instruction; there is also a "throwaway" seq number letting the server tell the receiver the oldest source state it may diff from. [issue #1087](https://github.com/mobile-shell/mosh/issues/1087)

## Eternal Terminal (ET): resumable TCP, no screen model

- ET is "a layer in between an application and unix TCP sockets that make the sockets robust to TCP disconnects including roaming and connection failure." It implements **Eternal TCP** with a BackedReader/BackedWriter: the reader tracks a byte sequence number; on reconnect it tells the other side the sequence number, and the writer re-sends the last M bytes (M = difference between writer and reader sequence numbers). Effectively a byte-level resumable stream. [eternalterminal.dev/howitworks](https://eternalterminal.dev/howitworks/)
- ET survives IP roaming and connection loss by this resumable TCP. On reconnect each side's BackedWriter resends accumulated data to catch up. [eternalterminal.dev/howitworks](https://eternalterminal.dev/howitworks/)
- Like Mosh, ET does **not** authenticate itself — it uses SSH to bootstrap: SSH launches an ETServer on the server with a short-lived password, sends the password to the client over the SSH channel, then the SSH connection is closed and client/server talk over a direct encrypted connection (magic-password authenticated). [eternalterminal.dev/howitworks](https://eternalterminal.dev/howitworks/)
- ET "does not implement any of the SSH protocol... simply creates a pseudo-terminal on the server side and connects this pseudo-terminal to the client's terminal." No channels. [eternalterminal.dev/howitworks](https://eternalterminal.dev/howitworks/)
- **Key difference from Mosh**: ET does **not** do terminal emulation or a screen model — it relays the raw terminal stream and re-sends the byte buffer on reconnect. Because it relays raw bytes, **native scrollback is preserved** (the terminal emulator is the client's, so its scrollback buffer survives). Commenter on LWN (MatejLach) notes "unlike mosh, it does support scrolling. On the other hand, typing is much more laggy than with mosh --predict=experimental." [eternalterminal.dev/howitworks](https://eternalterminal.dev/howitworks/) / [LWN comments](https://lwn.net/Articles/722923)
- ET supports tmux -CC ("tmux control center"); it "is supported in ET since it does not rely on the ssh protocol and is effectively its own protocol written in terminal escape sequences." Only iTerm2 (OS X) and an unsupported Terminator fork are mentioned as terminals that support tmux control center. [eternalterminal.dev/howitworks](https://eternalterminal.dev/howitworks/)
- ET had real-world latency problems: issue #120 documents random multi-second latency / lag spikes on a healthy LAN; logs show keepalive misses and repeated reconnect churn. Diagnosis eventually pointed at a port scanner hitting ET's server port 2022 and at server blocking while establishing new connections (later fixed with a "magic packet"). Lesson: ET's design (server holds the PTY, buffers on reconnect) is sensitive to connection churn and slow clients. [MisterTea/EternalTerminal issue #120](https://github.com/MisterTea/EternalTerminal/issues/120)
- ET also had crashes on network toggle in some 2018 branches (laptop wifi off → `Abort trap: 6`), later fixed. [issue #120](https://github.com/MisterTea/EternalTerminal/issues/120)
- ET "supports tmux -CC" (control mode) as one of the few clients to do so. [eternalterminal.dev/howitworks](https://eternalterminal.dev/howitworks/)

## tmux control mode (-CC): text protocol, %output + capture-pane

- Control mode is "a special mode that allows a tmux client to be used to talk to tmux using a simple text-only protocol. It was designed and written by George Nachman and allows his iTerm2 terminal to interface with tmux and show tmux panes using the iTerm2 UI." It sends tmux commands, receives output, and sends asynchronous notifications prefixed by `%`. [tmux Control Mode wiki](https://github.com/tmux/tmux/wiki/Control-Mode)
- `-C` starts a client in control mode; `-CC` disables canonical mode and most terminal features "intended for applications," and additionally sends a `\033P1000p` DSC sequence so a listening terminal can detect control mode entry. [tmux Control Mode wiki](https://github.com/tmux/tmux/wiki/Control-Mode)
- **Pane output** arrives as `%output` notifications with the pane ID and the raw output (bytes <32 and `\` octal-escaped). "any output in any pane in any window in the attached session is sent to the control client." This is the live stream. [tmux Control Mode wiki](https://github.com/tmux/tmux/wiki/Control-Mode)
- **Replay/redraw on attach**: control mode does not send a complete screen; because the client may have missed output (e.g. it dropped and reattached, or a big burst was paused), "It is up to the client to update the content of the pane if necessary, for example using `capture-pane`." So the standard pattern for a control-mode client to repaint is to run `capture-pane` (which dumps the pane's current visible content as text/escapes) and render it. [tmux Control Mode wiki](https://github.com/tmux/tmux/wiki/Control-Mode)
- `capture-pane -p` captures the current pane content; `-e` includes escape sequences; `-p` prints to stdout. This gives a full-screen snapshot that a client can render to reconstruct visible state. [tmux.info capture-pane guide](https://tmux.info/docs/commands/capture-pane) / [Baeldung "tmux Session Logging and Pane Content Extraction"](https://www.baeldung.com/linux/tmux-logging)
- **Flow control**: clients can set `pause-after=N` (via `refresh-client -f`); tmux pauses output to a pane when the client falls too far behind, sends `%pause` (or `%extended-output` with a "behind" ms value), and the client resumes with `refresh-client -A '%0:continue'`. "Once continued" tmux resends. This is tmux's answer to a slow/reconnecting client without buffering everything forever. [tmux Control Mode wiki](https://github.com/tmux/tmux/wiki/Control-Mode)
- **Cost / difficulty** of tmux -CC integration (stated by both George Nachman and wez): it's "black magic," "a fundamentally difficult problem," poorly documented — "there is little information about it, and lots of implicit knowledge is encoded into both tmux and iterm2." Maintenance pain: the client must know about every tmux version ever to polyfill features and work around bugs, plus client/server version skew. Also in-band signaling means an attacker-controlled host you ssh into can cause harmful text; and `wall` throws the protocol into chaos (no checksums/retries). [wezterm PtyMux discussion #4889 — gnachman & nicm comments](https://github.com/wezterm/wezterm/discussions/4889)
- iTerm2 renders full screen state on attach by holding pane state and, when connecting to a session, doing capture-pane-based syncs plus processing the live %output stream; but this implicit knowledge is exactly what makes third-party reimplementation costly. [wezterm PtyMux discussion #4889 — gnachman comment](https://github.com/wezterm/wezterm/discussions/4889)
- tmux keeps its own scrollback (history buffer) server-side, which is what enables capture-pane to reconstruct content on demand even after the client detaches. When a client attaches late, the flow-control + capture-pane mechanism is the documented way to get current + historic content. [tmux Control Mode wiki](https://github.com/tmux/tmux/wiki/Control-Mode)
- `send-keys -H` allows entering Unicode keys in hexadecimal; a few commands like `suspend-client` have no effect in control mode. Empty line (Enter) detaches the client. [tmux Control Mode wiki](https://github.com/tmux/tmux/wiki/Control-Mode)
- UNCERTAIN: whether tmux 3.x's unconditional alternate-screen behavior (the reason mobile-tty rejected tmux) is specific to how tmux programs its controlling terminal under a PTY; if a custom client used -CC over a bare PTY without an alternate screen, the alt-screen scrolling issue may differ. Not found in sources; flagged for verification.

## dtach: features, limitation, forks (dtach-rev), redraw/winch

- dtach "emulates the detach feature of screen... does not keep track of the contents of the screen, and thus works best with programs that know how to redraw themselves." It is a tiny relay: "dtach mostly acts as a relay, and does not mangle the text between the application and your terminal." [dtach.sourceforge.net](https://dtach.sourceforge.net/) / [dtach.1 man page](https://mankier.com/1/dtach)
- Because dtach does no terminal emulation and no screen model, **native scrollback and copy/paste keep working** (a reason to prefer it over tmux/mosh for a scrollback-based client). [Lobsters "alden: detachable terminal sessions without breaking scrollback" thread](https://lobste.rs/s/ybf4ss/alden_detachable_terminal_sessions) / [shpool README's dtach comparison](https://github.com/shell-pool/shpool)
- **No replay buffer**: "dtach simply loses any output programs make while they are detached." This is the exact gap mobile-tty's resize-nudge works around. [Lobsters comment — ilyagr](https://lobste.rs/s/ybf4ss/alden_detachable_terminal_sessions)
- **Redraw on attach** (this is dtach's built-in "repaint on reconnect"): on `-a`/attach, "the window size of the current terminal is sent to the master process, and a redraw is also requested." The redraw method is configurable via `-r <method>`: `none` (disabled), `ctrl_l` (send Ctrl-L if terminal is in character-at-a-time no-echo mode), or `winch` (force a WINCH/SIGWINCH signal to the program). Default is `ctrl_l`. [dtach.1 man page](https://mankier.com/1/dtach)
- History of the redraw approach: dtach 0.6 changed redraws from sending `^L` to sending a WINCH signal (to stop line-oriented programs like bash from clearing too much); 0.7 made it configurable and changed the default back to `^L` "since many programs only handle one or the other properly," and made the SIGWINCH handler re-install itself (systems that reset it). This directly documents why a resize/winch nudge is the right anti-plain-stall trick and why some programs need `^L` instead. [dtach changelog, sourceforge](https://dtach.sourceforge.net/)
- For a full-screen TUI like pi.dev, `-r winch` (which mobile-tty uses) is the modern approach, but note it is a *signal*, not a guaranteed repaint — the program must handle SIGWINCH by redrawing (pi.dev's wterm presumably does on resize). The `ctrl_l` method sends an actual Ctrl-L character, which many TUIs interpret as a redraw but some line-oriented programs treat as an input keystroke. [dtach.1](https://mankier.com/1/dtach) / [dtach changelog](https://dtach.sourceforge.net/)
- **Multi-attach**: dtach allows attaching multiple times to the same program; access is controlled only via Unix filesystem permissions (socket). It sets the executable bit on the socket when clients are attached (cleared when none attached). [dtach.sourceforge.net](https://dtach.sourceforge.net/)
- Modes: `-a` attach, `-A` attach-or-create, `-c` create+attach, `-n` create detached (daemonize), `-N` create detached stay in foreground, `-p` pipe stdin to a session. Detach char default `^\` (Ctrl-\), `-E` disables it, `-z` disables suspend-key processing. [dtach.1](https://mankier.com/1/dtach)
- No permission model beyond filesystem checks; master monitors session socket, the program, and attached terminals. [dtach.1](https://mankier.com/1/dtach)
- **dtach-rev** (bmills23, 2026): "a fork of dtach with a 256KB scrollback buffer for terminal session reconnection context." It adds a circular buffer capturing all PTY output, replays it to newly attaching clients, wraps replayed content in `\033]dtach-rev;replay-start\007` / `...-end\007` OSC sequences so smart clients can distinguish replay from live output, and adds a `-b <size>` flag (K/M suffixes, `0` to disable, default 256K). Motivation is exactly mobile-tty's: "for AI coding assistants running over SSH... losing context on reconnection is a significant problem." Installable via Homebrew tap `bmills23/terminallm`; conflicts with stock `dtach` binary. [github.com/bmills23/dtach-rev](https://github.com/bmills23/dtach-rev)
- UNCERTAIN: "dtach-plus" — no such notable upstream found; searching "dtach-plus" surfaces unrelated projects (the DetachHead/dtach GitHub is actually a fork of the Python `tach` dependency tool, an archived red herring, not a terminal). The actual relevant fork with scrollback/replay is `bmills23/dtach-rev`. [github.com/DetachHead/dtach](https://github.com/DetachHead/dtach) / [github.com/bmills23/dtach-rev](https://github.com/bmills23/dtach-rev)
- "resecure" — the dtach sourceforge project page shows no "resecure" component in fetched content; if it exists it is obscure. Not confirmed; flagged.

## abduco vs dtach

- abduco is "in many ways very similar to dtach but is a completely independent implementation which is actively maintained, contains no legacy code, provides a few additional features, [and] has a cleaner, more robust implementation," under the ISC license. [martanne/abduco README](https://github.com/martanne/abduco)
- Like dtach/abduco/mosh, shpool's README groups abduco and dtach together: "they eschew multiplexing and just send the raw bytes back to you for your local terminal to render" — native scrollback preserved. [shpool README](https://github.com/shell-pool/shpool)
- abduco's improvements over dtach (from its README):
  - session **list** (`abduco` with no args), marking which sessions have clients attached (`*`) and which terminated (`+`).
  - **session exit status** kept and reported on reconnection/termination.
  - **read-only sessions** via `-r` (all keyboard input ignored — passive observer); useful for sharing, e.g. via `socat -u` unidirectional proxy.
  - **better resize handling on shared sessions**: resize requests are only processed if initiated by the most recently connected, non-read-only client. (This is a real difference vs dtach for multi-attach resize semantics.)
  - **socket recreation** via SIGUSR1 to the server.
  - improved socket permissions (`$HOME/.abduco` or `/tmp/abduco/$USER`, owner-only). [martanne/abduco README](https://github.com/martanne/abduco)
- abduco detach key `^\` (Ctrl-\), configurable with `-e`; default command without args is dvtm. [martanne/abduco README](https://github.com/martanne/abduco)
- UNCERTAIN: whether abduco (like dtach) has any scrollback/replay buffer — sources indicate it is a raw relay like dtach ("simpler and cleaner alternative to tmux or screen"), and does **not** keep screen contents. The "re-print output produced while detached" hack is not claimed by abduco's README. [martanne/abduco README](https://github.com/martanne/abduco) / [Lobsters comment — ilyagr](https://lobste.rs/s/ybf4ss/alden_detachable_terminal_sessions)

## WezTerm multiplexer (PtyMux) and scrollback

- WezTerm has an existing terminal multiplexer with its own remote mux protocol (Unix/TLS/SSH domains) that resyncs clients that attach late; it is "effectively impossible" to consume outside of wezterm, which is why the author proposed a new, documented **PtyMux** protocol. [wezterm PtyMux discussion #4889](https://github.com/wezterm/wezterm/discussions/4889)
- Key flagged feature in the PtyMux design: "**Server-side terminal emulation to better facilitate session resumption and functions like navigating and searching scrollback.**" This is the same server-side-screen-model approach as Mosh/tmux. [wezterm PtyMux discussion #4889](https://github.com/wezterm/wezterm/discussions/4889)
- In the discussion, however, one reply argued server-side emulation is NOT strictly necessary: "Like dtach or abduco, stdout/stderr is streamed as-is... it'd allow greater flexibility." The author answered it's optional: "It's not necessary; it's an optional feature in my protocol design."

  [wezterm PtyMux discussion #4889 — scabala & wez](https://github.com/wezterm/wezterm/discussions/4889)
- PtyMux was intended to be usable over `ssh machine /path/to/ptymux --server` over stdin/stdout (no new ports/auth), framed with BSON. Status: "I have some designs and a partial implementation inside wezterm... has stalled" (no other terminal authors collaborated). [wezterm PtyMux discussion #4889](https://github.com/wezterm/wezterm/discussions/4889)
- WezTerm's mux protocol runs over existing SSH domains without extra open ports and supports attaching to existing sessions (spawn/attach). [wezterm.org multiplexing docs](https://wezterm.org/multiplexing.html)

## Cheap "server keeps scrollback and replays on attach" techniques

- The domain of solutions divides into (a) **screen-model / terminal-emulation servers** (tmux, screen, mosh, wezterm mux, shpool via shpool_vt100) that keep an in-memory render and can redraw the whole view on attach, and (b) **raw relays** (dtach, abduco, ET-style resumable TCP) that either lose output while detached or must buffer raw bytes and re-send them. [shpool README](https://github.com/shell-pool/shpool) / [Lobsters thread](https://lobste.rs/s/ybf4ss/alden_detachable_terminal_sessions)
- **tmux capture-pane loop**: tmux keeps its own per-pane scrollback server-side; `capture-pane -p -e` dumps the current visible pane (with escapes), so a custom client that attaches late can render `capture-pane` output to replay the screen. Combined with control-mode flow control (`pause-after` + `refresh-client -A...continue`), tmux provides both live stream and on-demand full repaint. This is the documented "cheap" replay primitive for a control-mode client. [tmux Control Mode wiki](https://github.com/tmux/tmux/wiki/Control-Mode) / [tmux.info capture-pane](https://tmux.info/docs/commands/capture-pane)
- **shpool's approach** (a lighter tmux alternative that keeps native scrollback): it "does not do any rendering and subsetting of the shell output" normally, but "continually maintains an in-memory render of the terminal state via the shpool_vt100 crate. On reattach, shpool will use this in-memory render to re-draw the screen, so you can easily see where you were when your connection dropped. This even allows you to see output generated after your connection dropped." This is a middle path: raw relay during normal operation + vt100 emulation only for repaint on reattach. [shpool README](https://github.com/shell-pool/shpool)
- **dtach-rev's approach** (fork of dtach): keep a raw circular byte buffer (256KB default) and replay it on attach, marking replay with OSC delimiters for the client to distinguish from live output. Much simpler than full terminal emulation — it does not re-render a screen model, just replays the last raw bytes. Caveat from the Lobsters thread: replaying raw bytes works well for simple line programs but "would work terribly for a TUI if, when the program is attached, the terminal is in a different state than when detach happened (e.g. different size, but even a different cursor position might be bad)." [github.com/bmills23/dtach-rev](https://github.com/bmills23/dtach-rev) / [Lobsters comment — ilyagr](https://lobste.rs/s/ybf4ss/alden_detachable_terminal_sessions)
- Three options for handling output produced while detached (from the Lobsters alden analysis), paraphrased: (1) save all output and reprint it on attach — OK for simple programs, terrible for TUIs whose terminal state changed; (2) emulate a terminal like mosh/tmux/screen — tmux also keeps last X lines of scrollback; (3) forget output while detached and send a redraw command on reattach (SIGWINCH / Ctrl-L) — the messy compromise dtach actually takes. [Lobsters comment — ilyagr](https://lobste.rs/s/ybf4ss/alden_detachable_terminal_sessions)
- detached.el (Emacs) implements option (1) as a layer over dtach for non-TUI programs. [Lobsters comment — lnikkila](https://lobste.rs/s/ybf4ss/alden_detachable_terminal_sessions)

## Real-world mobile/phone network reliability (WiFi sleep, carrier NAT)

- Mosh explicitly targets these: "It's more robust and responsive, especially over Wi-Fi, cellular, and long-distance links." Roaming and intermittent-connectivity support are core. [mosh.org](https://mosh.org/)
- The client sends a UDP heartbeat "at least once every three seconds," and the server updates its target IP from any newer authentic client packet — so carrier NAT rebinding or WiFi→LTE handoff without the client knowing its IP changed still reconnects seamlessly. "Roaming works even when the client is not aware that its Internet-visible IP address has changed." [mosh.org](https://mosh.org/)
- Desktop sleep/resume / WiFi drop: "put your laptop to sleep and wake it up later, keeping your connection intact. If your Internet connection drops, Mosh will warn you — but the connection resumes when network service comes back." The client notices connectivity loss before the OS does, warns the user. [mosh.org](https://mosh.org/) / [LWN](https://lwn.net/Articles/722923)
- Mosh was designed against bufferbloat (deep packet queues on loaded wireless) and link-layer retransmission delays, which are the real mobile pain points (multi-second delays when loaded), and it avoids draining TCP-style buffers so Control-C always works. [;login: essay](https://www.usenix.org/system/files/login/articles/winstein.pdf) / [mosh.org FAQ](https://mosh.org/)
- ET survives roaming via resumable TCP (BackedReader/BackedWriter byte replay), but its keepalive scheme (client KEEP_ALIVE_DURATION=5s, server 7s) proved fragile under churn: "Missed a keepalive, killing connection" while the packet actually arrived — a keepalive-driven reconnect loop. And it suffered DoS/latency from unrelated inbound connections to its server port. Lesson: keepalive tolerance and server non-blocking matter on mobile. [ET issue #120](https://github.com/MisterTea/EternalTerminal/issues/120)
- ET's client previously died (`Abort trap: 6`) when toggling wifi off in some 2018 builds; fixed. [ET issue #120](https://github.com/MisterTea/EternalTerminal/issues/120)
- **Why mobile clients want a telltale "am I still connected" signal**: unlike SSH (which silently hangs until you type and it dies), Mosh warns when it hasn't heard from the server. This is an actionable UX feature for a mobile web terminal. [mosh.org](https://mosh.org/)
- UNCERTAIN: ET's exact behavior for scrollback/replay vs. raw byte resend on mobile reconnect (whether a detached client's terminal history survives) — sources say ET "supports scrolling" (native scrollback) via raw relay, but do not detail a server-side replay buffer; the resend is byte-level via sequence numbers, meaning the *client's own terminal emulator* must already have rendered those bytes to give scrollback. Finding not fully specified in ET docs. [eternalterminal.dev/howitworks](https://eternalterminal.dev/howitworks/) / [LWN comments](https://lwn.net/Articles/722923)
