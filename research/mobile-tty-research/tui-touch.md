# Research: tui touch

## Mouse event models exposed by TUI frameworks

- **crossterm (the backend ratatui uses)** exposes `MouseEventKind` with exactly 8 variants: `Down(button)`, `Up(button)`, `Drag(button)`, `Moved`, `ScrollDown`, `ScrollUp`, `ScrollLeft`, `ScrollRight`. There is no tap/long-press/gesture concept [crossterm MouseEventKind](https://docs.rs/crossterm/latest/crossterm/event/enum.MouseEventKind.html)
- crossterm documents a portability caveat directly relevant to synthesized touch: "Some platforms/terminals do not report mouse button for the `MouseEventKind::Up` and `MouseEventKind::Drag` events. `MouseButton::Left` is returned if we don't know which button was used." [crossterm MouseEventKind](https://docs.rs/crossterm/latest/crossterm/event/enum.MouseEventKind.html)
- **ratatui itself has no mouse abstraction.** The ratatui docs page on mouse capture is three paragraphs and explicitly punts: "Each backend handles mouse capture differently, with variations in the types of events that can be captured and how they are represented. As such, the behavior may vary depending on the backend being used, and developers should consult the specific backend's documentation" [ratatui mouse-capture.md](https://raw.githubusercontent.com/ratatui/ratatui-website/main/src/content/docs/concepts/backends/mouse-capture.md)
- **Bubble Tea (v2/main)** splits mouse into four message types: `MouseClickMsg`, `MouseReleaseMsg`, `MouseWheelMsg`, `MouseMotionMsg`, all wrapping a `Mouse{X, Y int; Button MouseButton; Mod KeyMod}`. Coordinates are zero-based with (0,0) at upper left [bubbletea mouse.go](https://github.com/charmbracelet/bubbletea/blob/main/mouse.go)
- Bubble Tea's button constants are explicitly "based on X11 mouse button codes" — 1 left, 2 middle, 3 right, 4/5 wheel up/down, 6/7 wheel left/right, 8/9 browser back/forward, plus `MouseButton10`/`11`. Comment states "Other buttons are not supported." [bubbletea mouse.go](https://github.com/charmbracelet/bubbletea/blob/main/mouse.go)
- Bubble Tea mouse modes are `MouseModeNone`, `MouseModeButton` (press/release), `MouseModeMotion` (motion while button held = drag), `MouseModeAllMotion` (all cursor movement). Set via the `tea.View` struct in current main [bubbletea Mouse Input](https://deepwiki.com/charmbracelet/bubbletea/3.2-mouse-input)
- Bubble Tea delegates low-level mouse parsing to `github.com/charmbracelet/ultraviolet`; `MouseButton` is a type alias for `uv.MouseButton` [bubbletea Mouse Input](https://deepwiki.com/charmbracelet/bubbletea/3.2-mouse-input)
- **Textual** exposes `MouseMove`, `MouseDown`, `MouseUp`, `Click`, `Enter`, `Leave`, `MouseCapture`, `MouseRelease`, `MouseScrollUp/Down` and (for terminals supporting horizontal wheel) `MouseScrollLeft/Right` [Textual Input guide](https://raw.githubusercontent.com/Textualize/textual/main/docs/guide/input.md)
- Textual explicitly recommends `Click` over `MouseDown`/`MouseUp`, with forward-looking language about non-mouse pointers: "This is because a future version of Textual may support other pointing devices which don't have up and down states." [Textual Input guide](https://raw.githubusercontent.com/Textualize/textual/main/docs/guide/input.md)
- Textual notes "The trackpad (and possibly other pointer devices) are treated the same as the mouse in terminals" and "Terminal emulators will typically convert trackpad gestures into scroll events." No mention of touch [Textual Input guide](https://raw.githubusercontent.com/Textualize/textual/main/docs/guide/input.md)
- Textual has a `<pointer>` CSS type and a `pointer` style in its reference, but no touch/gesture events in its event list [Textual events index](https://textual.textualize.io/guide/input/)
- **Bubble Tea hit-testing is a known pain point.** BubbleZone was written because "the app root can't realistically keep track of that information in a sane way" once components nest (`app root > active viewport > table > table rows`). It works by injecting invisible marker sequences into rendered output (`zone.Mark(id, view)`), scanning/stripping them at the root (`zone.Scan()`), then answering `zone.Get(id).InBounds(mouseEvent)` [Meet BubbleZone](https://liam.sh/p/meet-bubblezone)
- Bubble Tea's current answer for the same problem is `lipgloss.Compositor` layer hit testing (see `examples/clickable`) [bubbletea Mouse Input](https://deepwiki.com/charmbracelet/bubbletea/3.2-mouse-input)

## Terminal mouse wire protocol (SGR 1006 and relatives)

- Tracking modes and encoding modes are **separate**. Tracking: `9` (X10, press only), `1000` (VT200 normal, press+release), `1002` (button-event, motion while held), `1003` (any-event, all motion). Encoding: `1005` (UTF-8), `1006` (SGR cell), `1015` (urxvt), `1016` (SGR pixel) [sharp-vision mouse.md](https://github.com/pavkam/sharp-vision/blob/main/docs/protocols/mouse.md)
- Mode 1006 "does not enable mouse tracking on its own; it must be used in combination with a mouse tracking mode (Mode 1000, 1002, or 1003)" [vtdn SGR mouse](https://vtdn.dev/docs/decset/mode1006-sgr-mouse/)
- SGR wire format: `CSI < Cb ; Cx ; Cy M` for press/motion, lowercase `m` for release. `Cx`/`Cy` are 1-based decimal. Parse regex given as `\e\[<(\d+);(\d+);(\d+)([Mm])` [vtdn SGR mouse](https://vtdn.dev/docs/decset/mode1006-sgr-mouse/)
- SGR button encoding: `0` left, `1` middle, `2` right, `+32` motion flag, `64` wheel up, `65` wheel down. Modifier bits: `4` shift, `8` meta/alt, `16` control [vtdn SGR mouse](https://vtdn.dev/docs/decset/mode1006-sgr-mouse/)
- Concrete examples: left click at col 10 row 5 = press `\e[<0;10;5M`, release `\e[<0;10;5m`. Ctrl+click at col 300 row 100 = `\e[<16;300;100M` [vtdn SGR mouse](https://vtdn.dev/docs/decset/mode1006-sgr-mouse/)
- Enable with `printf '\e[?1000h\e[?1006h'`, disable with `printf '\e[?1006l\e[?1000l'` [vtdn SGR mouse](https://vtdn.dev/docs/decset/mode1006-sgr-mouse/)
- Advantages over X10 encoding: no 223-coordinate limit (X10 packs coords into single bytes with +32 offset); release events are distinguishable per-button (X10 reports button 3 for all releases with no way to tell which) [vtdn SGR mouse](https://vtdn.dev/docs/decset/mode1006-sgr-mouse/)
- **SGR 1006 support is near-universal**, including xterm.js since 2.0.1, tmux since 1.8, GNU Screen since 4.7.0, Zellij since 0.31.2, and every modern emulator listed [vtdn SGR mouse — terminal support table](https://vtdn.dev/docs/decset/mode1006-sgr-mouse/)
- The protocol carries **no notion of tap duration, pressure, touch identity, or multi-touch**. The wire vocabulary is button number + modifier bits + cell coordinates + press/release [vtdn SGR mouse](https://vtdn.dev/docs/decset/mode1006-sgr-mouse/), [sharp-vision mouse.md](https://github.com/pavkam/sharp-vision/blob/main/docs/protocols/mouse.md)
- Mode 1016 (SGR pixel) reports pixel coordinates instead of cells; SharpVision derives cells as `floor(pixel * cellCount / pixelCount)` and flags them `CellPositionInferred` [sharp-vision mouse.md](https://github.com/pavkam/sharp-vision/blob/main/docs/protocols/mouse.md)

## Touch → mouse translation: what mobile terminals actually do, and what breaks

- **Termux maps one-finger drag to scroll-wheel events, not drag.** Maintainer fornwall: "We currently translate dragging the finger to scroll wheel events to enable scrolling e.g. output in tmux. The reasoning it that it's hard to drag things with precision using a finger, so we might just as well enable scrolling in that case." Issue open since 2019 [termux-app #1384](https://github.com/termux/termux-app/issues/1384)
- Consequence stated by the reporter: "While this is cute it prevents implementing any kind of advanced mouse functionality in Termux, like dragging." [termux-app #1384](https://github.com/termux/termux-app/issues/1384)
- Termux distinguishes finger from real mouse via `e.isFromSource(InputDevice.SOURCE_MOUSE)`; with a real mouse, drag-while-held works [termux-app #1384](https://github.com/termux/termux-app/issues/1384)
- Long-press collides with terminal chrome: "if you press down and hold steady for 0.5 seconds a copy/paste dialog is triggered, even when mouse mode is enabled." Suggested workarounds in thread: two-finger long press for selection, ctrl-modified single-finger press for the menu, alt-click for right-button [termux-app #1384](https://github.com/termux/termux-app/issues/1384)
- Suggested gesture vocabulary from the same thread (from a MUD client author): translate "a crude drag into a swipe event... 8 swipe directions", plus explicit drag-up/drag-down to mimic vertical scroll; two-finger drag for wheel; horizontal wheel support [termux-app #1384](https://github.com/termux/termux-app/issues/1384)
- A commenter asks for a live toggle between drag-mode and scroll-mode "e.g. with a button in the extra keys row. Since scrolling is common in tmux and weechat, using two fingers for that would be impractical" [termux-app #1384](https://github.com/termux/termux-app/issues/1384)
- **The core mobile conflict: mouse tracking eats scrollback.** "The xterm control sequence for mouse tracking (code 1000 or 1006) also captures scroll events, reporting them as button codes 64 and 65. This is necessary for apps in alternate screen mode, but hurts usability in regular screen mode because it blocks viewport scrollback." [termux-app #4302](https://github.com/termux/termux-app/issues/4302)
- Same issue on why touch makes this worse: "On a touchscreen, it's far easier to move the cursor in a readline prompt by tapping the screen than by using the soft arrow keys... but turning on the feature blocks scrollback, and worse — an accidental swipe of the screen may invoke unwanted functionality." Example given: a zsh mouse plugin remaps scroll to history navigation, so a sloppy tap can erase user input [termux-app #4302](https://github.com/termux/termux-app/issues/4302)
- Pushback from a Termux contributor against a per-terminal preference: "Different terminals behaving differently often ends up with a mess for applications that has to have logic based on which terminal it's running in. And this isn't really something a user should decide on" [termux-app #4302](https://github.com/termux/termux-app/issues/4302)
- **Blink Shell (iOS) position:** "As an iPad application, Blink Shell comes with out-of-the-box touch and mouse support. In SSH, it works right away. Mosh users need to use `tmux` or other terminal multiplexers as it doesn't support scrolling." The documented enablement is app-side config: tmux `set -g mouse on`, vim `set mouse=a`, emacs `(xterm-mouse-mode 1)` [blink #1528](https://github.com/blinksh/blink/discussions/1528)
- UNCERTAIN whether iOS terminals distinguish gestures at protocol level: Blink's maintainer answer treats touch as plain mouse and offers no gesture vocabulary [blink #1528](https://github.com/blinksh/blink/discussions/1528), while Termux explicitly synthesizes wheel from single-finger drag [termux-app #1384](https://github.com/termux/termux-app/issues/1384) — i.e. behavior is per-client and unspecified, not standardized

## TUI-side proposals to make touch/primary-screen mouse workable

- **Contour's Passive Mouse Tracking (`CSI ? 2029 h`)** is a proposed VT extension aimed exactly at the primary-screen case: "let the application receive mouse events, while still allowing the user to select text on the screen with the mouse or scroll the viewport with the mouse wheel" [passive-mouse-tracking.md](https://github.com/contour-terminal/vt-extensions/blob/master/passive-mouse-tracking.md)
- Enabling 2029 "will implicitly activate DEC mode ?1006 (SGR) as well as ?1002 (Button click event tracking)"; `CSI ? 2029 ; 1003 h` adds motion. Only SGR transport is allowed. `CSI ? 2029 l` clears everything in one sequence [passive-mouse-tracking.md](https://github.com/contour-terminal/vt-extensions/blob/master/passive-mouse-tracking.md)
- Key semantic limit for a scrolling client: "the application will only receive mouse events for the main page area and not for the 'scrollback' buffer"; coordinates are reported relative to the page, so a viewport scrolled up 5 lines still reports the top cell as (1,1) [passive-mouse-tracking.md](https://github.com/contour-terminal/vt-extensions/blob/master/passive-mouse-tracking.md)
- Adoption table shows **Contour only** — xterm.js, Windows Terminal, mintty, notcurses, foot, WezTerm, VTE, iTerm2, Kitty, Alacritty, Konsole, st all marked "n/a" [passive-mouse-tracking.md](https://github.com/contour-terminal/vt-extensions/blob/master/passive-mouse-tracking.md)
- A Termux contributor raised a concrete objection to 2029 for tap-to-move-cursor: "it says to report the same coordinates regardless of scroll position... how would the shell know the difference between clicking on the last line vs. clicking on the second last line with one line scrolled up" [termux-app #4302](https://github.com/termux/termux-app/issues/4302)
- **The already-shipped alternative is terminal-side synthesis of arrow keys.** "several terminal emulators already implement the feature you're asking for... without any mouse reporting to the shell. The way they do it is to have the terminal send left/right arrow key sequences to the shell to move the cursor to where you click. This is supported in at least kitty, xterm, iTerm2, Konsole and DomTerm." [termux-app #4302](https://github.com/termux/termux-app/issues/4302)
- xterm gates this behind mode `\e[?2001h` ("Enable readline mouse button-1"); kitty/iTerm2/Konsole/DomTerm instead require the **shell to emit OSC 133 prompt markers** so the terminal knows where the prompt starts [termux-app #4302](https://github.com/termux/termux-app/issues/4302)
- Ghostty documents the same mechanism and its limits: "This feature requires shell integration (specifically prompt marking via OSC 133) and only works in primary screen mode... it works by translating your desired position into a series of synthetic arrow key movements, so some weird behavior [may occur]" [Ghostty docs, quoted in termux-app #4302](https://github.com/termux/termux-app/issues/4302)
- Mode 2001 caveat noted in thread: "the 2001 mode is only supposed to work if the text cursor is on the same line as the mouse cursor, which is somewhat limiting on portrait-oriented screens" [termux-app #4302](https://github.com/termux/termux-app/issues/4302)
- iTerm2 shipped a "disable reporting mouse events" preference in response to this thread, but it "applies to both main and alt screen" [termux-app #4302](https://github.com/termux/termux-app/issues/4302), [iTerm2 issue 12076](https://gitlab.com/gnachman/iterm2/-/issues/12076)
- Contour's vt-extensions repo also contains `text-selection-tracking.md`, `clipboard-extension.md`, and `synchronized-output.md` [contour vt-extensions](https://github.com/contour-terminal/vt-extensions)

## pi-tui (the actual target app) — terminal features it relies on

- pi-tui is described as "Minimal terminal UI framework with differential rendering and synchronized output for flicker-free interactive CLI applications" [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- It ships **two renderers behind one `TUI` interface**: `TuiMainScreen` "renders into the main terminal buffer and preserves terminal scrollback", and `TuiAltScreen` "renders a fixed-height viewport in the alternate terminal buffer with application-owned scrolling. When stopped, it restores the main buffer and prints the complete final document." [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- Listed features include: "**Synchronized Output**: Uses CSI 2026 for atomic screen updates (no flicker)"; "**Bracketed Paste Mode**: Handles large pastes correctly with markers for >10 line pastes"; "**Inline Images**: Renders images in terminals that support Kitty or iTerm2 graphics protocols" [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- **Mouse is alt-screen only.** "Application-owned Scrolling: Alternate-screen viewport supports mouse, trackpad, and keyboard navigation." Layout semantics (`VStack`/`HStack`/`ScrollView`) "are intentionally unavailable on `TuiMainScreen`, where the terminal owns scrollback." [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- Alt-screen wheel routing: "Mouse-wheel input targets the scroll view under the pointer and unused delta chains to outer scroll views by default. The primary scroll view receives the alternate-screen keyboard navigation actions and wheel input over non-scrollable regions." [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- pi-tui's alt-screen scroll view "can also jump between OSC 133 semantic prompt markers, matching common terminal prompt-navigation shortcuts" [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- **pi-tui already has width-responsive hooks.** Stack entries support `basis`, `grow`, `shrink`, `minSize`, `maxSize`, and "responsive `visible` callbacks". Overlays take `visible: (termWidth, termHeight) => termWidth >= 100 // Hide on narrow terminals` [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- Overlay sizing defaults to "centered, max 80 cols" with `minWidth` floor, percentage or absolute `row`/`col`, `margin` clamping to terminal bounds, and anchors `center`/`top-left`/`bottom-right`/etc. [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- **Hard width contract**: `render(width)` "Returns an array of strings, one per line. Each line **must not exceed `width`** or the TUI will error." Helpers `truncateToWidth()` and `wrapTextWithAnsi()` are provided [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- pi-tui's `Editor` documents modifier-key fragility that matters on a soft keyboard: "`Shift+Enter`, `Ctrl+Enter`, or `Alt+Enter` - New line (terminal-dependent, **Alt+Enter most reliable**)" [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- Cursor handling: pi-tui renders a fake cursor and keeps the hardware cursor hidden by default, positioning it via a zero-width APC `CURSOR_MARKER` scanned out of rendered output, "for terminals that track IME candidate windows with hidden cursors". Enable a visible hardware cursor with `showHardwareCursor`, `setShowHardwareCursor(true)`, or `PI_HARDWARE_CURSOR=1` [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- pi-tui appends a full SGR reset and OSC 8 reset to the end of every rendered line; styles do not carry across lines [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- Built-in `TruncatedText` exists specifically for "status lines and headers" that must fit the viewport [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)

## Synchronized output (CSI 2026) and modern AI-CLI terminal requirements

- Sequences: `\x1b[?2026h` begin, `\x1b[?2026l` end. Terminal buffers writes between them and applies them as one atomic frame [RuleSell CSI 2026](https://www.rulesell.com/topic/csi-2026-synchronized-output)
- Canonical spec is Christian Parpart's gist (Contour maintainer), dating to 2020 [Parpart synchronized output gist](https://gist.github.com/christianparpart/d8a62cc1ab659194337d73e399004036)
- Unknown DEC private modes are no-ops, so it degrades cleanly on terminals that lack it [RuleSell CSI 2026](https://www.rulesell.com/topic/csi-2026-synchronized-output)
- There is an inactivity timeout so a crashed program can't lock the screen — "typically 150-300ms depending on emulator". The article flags this as unverified: "The 150-300ms timeout varies. Spec leaves it implementation-defined. We don't have a canonical table of per-terminal timeout values." [RuleSell CSI 2026](https://www.rulesell.com/topic/csi-2026-synchronized-output)
- Correctness notes given: pair every begin with an end; **don't nest** ("Most terminals don't track nested sync regions correctly"); flush after each write; test inside tmux [RuleSell CSI 2026](https://www.rulesell.com/topic/csi-2026-synchronized-output)
- Claimed support as of May 2026: iTerm2, WezTerm (post-Feb-2026 fixes), Alacritty, Kitty, Ghostty, Windows Terminal, Warp, Contour. tmux supports it in current versions; "Version mismatch between your tmux and your terminal is the most common silent failure source." Basic xterm ignores it cleanly [RuleSell CSI 2026](https://www.rulesell.com/topic/csi-2026-synchronized-output)
- Cited real-world breakage: claude-code issue #37283 (tmux flicker, fixed by emitting sync sequences) and #41965 (v2.1.89 regression that broke them again) [RuleSell CSI 2026](https://www.rulesell.com/topic/csi-2026-synchronized-output)
- **Explicitly flagged as an open gap and directly relevant here**: "Mobile terminals. SSH clients on iOS and Android (Termius, Blink Shell, etc.) have varying sync support that we have not audited." [RuleSell CSI 2026](https://www.rulesell.com/topic/csi-2026-synchronized-output)
- UNCERTAIN: this source is an SEO-style aggregator page, not a primary source. Its terminal support table and the "150-300ms" figure should be verified against Parpart's gist and per-terminal docs before relying on them [RuleSell CSI 2026](https://www.rulesell.com/topic/csi-2026-synchronized-output) vs [Parpart gist](https://gist.github.com/christianparpart/d8a62cc1ab659194337d73e399004036)

## Kitty keyboard protocol (progressive enhancement)

- Sequences: `CSI > flags u` push+enable, `CSI < u` pop, `CSI ? u` query (terminal replies `CSI ? flags u`). Stack depth of at least 8 should be supported [vtdn kitty keyboard](https://vtdn.dev/docs/keyboard/kitty-keyboard)
- Flags bitmask: `1` disambiguate escape codes, `2` report event types (press/repeat/release), `4` report alternate keys (shifted + base layout), `8` all keys as escape codes, `16` report associated text. `\e[>31u` enables everything [vtdn kitty keyboard](https://vtdn.dev/docs/keyboard/kitty-keyboard)
- Key event format at its fullest: `CSI key_code : shifted_key : base_key ; modifiers : event_type ; text u`. Modifiers are bitmask+1: Shift 1, Alt 2, Ctrl 4, Super 8, Hyper 16, Meta 32, CapsLock 64, NumLock 128 [vtdn kitty keyboard](https://vtdn.dev/docs/keyboard/kitty-keyboard)
- The ambiguities it fixes are exactly the ones a soft-keyboard client hits: Enter vs Ctrl+M (`0x0d`), Tab vs Ctrl+I (`0x09`), Backspace vs Ctrl+H/Ctrl+? (`0x7f`/`0x08`), Escape vs Ctrl+[ vs Alt-prefix (`0x1b`) [vtdn kitty keyboard](https://vtdn.dev/docs/keyboard/kitty-keyboard)
- Textual independently documents the same limitation from the app side: "the `Tab` key is indistinguishable from `Ctrl`+`I` in the terminal", hence its `aliases` attribute containing `["tab", "ctrl+i"]` [Textual Input guide](https://raw.githubusercontent.com/Textualize/textual/main/docs/guide/input.md)
- **xterm.js supports it** but gated: "Requires `vtExtensions.kittyKeyboard` option, added after 6.0.0". WezTerm requires `enable_kitty_keyboard`. Windows Terminal added full support Feb 2026. xterm, PuTTY, st, urxvt, Konsole, VTE: no [vtdn kitty keyboard — terminal support table](https://vtdn.dev/docs/keyboard/kitty-keyboard)
- tmux support is partial ("~"): extended keys protocol (`CSI 27;mods;key~` and `CSI key;mods u`) since 3.2, revamped in 3.5 [vtdn kitty keyboard](https://vtdn.dev/docs/keyboard/kitty-keyboard)

## In-band resize (mode 2048) — relevant to a client that resizes constantly

- `CSI ? 2048 h` enables; terminal then emits `CSI 8 ; rows ; cols t` in the input stream on every resize. `CSI ? 2048 l` disables. Query support via `CSI ? 2048 $p` → `CSI ? 2048 ; Ps $ y` (Ps=1 set, 2 reset, 0 unrecognized) [vtdn in-band resize](https://vtdn.dev/docs/decset/mode2048-in-band-resize/)
- Stated SIGWINCH problems it solves: not in-band (app can't tell where in input processing the resize happened); "Lost through SSH... must be forwarded by the SSH client... can be unreliable"; lost/lossy through multiplexers; race conditions where "If multiple resizes happen quickly, intermediate SIGWINCH signals may be coalesced" and a follow-up `ioctl` "may return a stale value" [vtdn in-band resize](https://vtdn.dev/docs/decset/mode2048-in-band-resize/)
- **Support is thin**: foot 1.19.0, Ghostty v1.0.0, iTerm2 nightly, Kitty. Explicitly **not** supported by Alacritty, contour, Konsole, mintty, PuTTY, Rio, st, VTE ("Mode defined but not implemented"), WezTerm, Windows Terminal, xterm [vtdn in-band resize — terminal support table](https://vtdn.dev/docs/decset/mode2048-in-band-resize/)
- Spec is a gist by Tim Culverhouse (rockorager) [In-Band Resize gist](https://gist.github.com/rockorager/e695f2f3a12087ddf998ef96210e5364)
- Guidance: "Applications should still handle SIGWINCH as a fallback for terminals that do not support Mode 2048. The two mechanisms can coexist safely." [vtdn in-band resize](https://vtdn.dev/docs/decset/mode2048-in-band-resize/)

## Alternate screen behavior

- Standard framing: alt screen is "a separate buffer... when the application exits, the terminal will switch back to the main screen, and the contents of the alternate screen will be cleared" [ratatui alternate-screen.md](https://raw.githubusercontent.com/ratatui/ratatui-website/main/src/content/docs/concepts/backends/alternate-screen.md)
- ratatui warns "not all terminal emulators support the alternate screen, and even those that do may handle it differently" [ratatui alternate-screen.md](https://raw.githubusercontent.com/ratatui/ratatui-website/main/src/content/docs/concepts/backends/alternate-screen.md)
- The scrollback/mouse tradeoff is the recurring axis: mouse tracking "is necessary for apps in alternate screen mode, but hurts usability in regular screen mode because it blocks viewport scrollback" [termux-app #4302](https://github.com/termux/termux-app/issues/4302)
- pi-tui encodes the same split architecturally — main screen = terminal owns scrollback and no layout/scroll semantics; alt screen = app owns scrolling and gets mouse [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- Relevant DEC modes catalogued: `?1049` enter/exit alt screen, `?1047` alt screen clear-on-enter, `?47` legacy alt screen, `?1007` alt-scroll (wheel→arrow keys), plus a distinct "Alt screen separate scrollback" behavior [terminfo.dev modes index](https://terminfo.dev/modes), [terminfo.dev scrollback](https://terminfo.dev/scrollback)
- Mode 1007 (alt-scroll) is explicitly neutralized under passive mouse tracking: "While mode `?2029` is active, mode `?1007` has no effect (i.e. wheel events are not translated to arrow keys)" [passive-mouse-tracking.md](https://github.com/contour-terminal/vt-extensions/blob/master/passive-mouse-tracking.md)

## Small-screen / narrow-width TUI behavior

- **The dominant pattern is a hard minimum-size gate, not reflow.** A widely-circulated TUI design skill states the rule bluntly: "Minimum size gate. Display 'terminal too small' if below usable minimum." [tui-design skill](https://claudeskills.info/skills/pedronauck/skills/tui-design/)
- **btop's threshold is width ≤ 80 or height ≤ 24**, at which it shows a warning screen. In v1.2.3 that screen also swallowed `q`, so the app couldn't be quit (Ctrl+C still worked); fixed in a later release [btop #926](https://github.com/aristocratos/btop/issues/926)
- **lazygit already switches to a vertical/stacked layout when the terminal gets small**, and users ask to force it permanently: "Is it possible to have lazygit always use a vertical layout, like it does when the terminal gets small? I enjoy this layout since it allows the most [room]" [lazygit #3036](https://github.com/jesseduffield/lazygit/discussions/3036)
- Ratatui's constraint-based layout is the responsive mechanism, with nesting and `.spacing(u16)`; there is no built-in minimum-size guard [ratatui Layout](https://ratatui.rs/concepts/layout/), [ratatui layout system](https://deepwiki.com/ratatui/ratatui-website/2.2-layout-system)
- Ratatui has a documented FAQ entry "How do I avoid panics due to out of range calls on the Buffer?" — small areas are a real failure mode, not just a cosmetic one [ratatui FAQ](https://ratatui.rs/faq/)
- Ratatui has an open bug in the opposite direction too: footer widgets rendering "near the top and split across multiple lines" in very large terminals [ratatui #2167](https://github.com/ratatui/ratatui/issues/2167)
- Textual's responsive tools are CSS-side: `min-width`, `max-width`, `min-height`, `max-height`, `text-overflow`, `text-wrap`, `dock`, and grid — but no width-based media-query construct appears in the styles reference [Textual styles reference](https://textual.textualize.io/guide/input/)
- pi-tui's approach is imperative rather than declarative: `visible: (termWidth, termHeight) => termWidth >= 100` callbacks evaluated each frame [pi-tui README](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- Claude Code has open issues about width handling: "Terminal UI not filling full width - right side truncated in iTerm2" [claude-code #45556](https://github.com/anthropics/claude-code/issues/45556) and "[FEATURE] Force table rendering independent of terminal width / font" [claude-code #68839](https://github.com/anthropics/claude-code/issues/68839)
- Broader context on the 80-column default and pushback against it [Lobsters: 80-column terminals in 2020](https://lobste.rs/s/7mwlep/no_80_column_terminals_2020_isn_t)
- I did **not** find any documented column-count threshold or workaround specific to ~50 columns for lazygit, btop, or vim/neovim. Nothing in the sources surveyed addresses sub-60-column layouts as a supported target

## xterm.js and browser-terminal touch state (relevant prior art for a DOM renderer)

- Open issue "Limited touch support on mobile devices impacts terminal usability" (filed 2025-07-20, still open) lists what does not work: touch scrolling, pinch-to-zoom, touch text selection, long press for context menu, double tap for word selection. States "Mobile experience relies on browser's mouse event translation" and "no dedicated touch event handling" in `CoreBrowserTerminal.ts` [xterm.js #5377](https://github.com/xtermjs/xterm.js/issues/5377)
- Maintainer jerch: "the gist of mobile device support - it is non-existent (beside what the mobile browsers try to achieve by limited automapping of events and stuff). Our whole frontend handling is very desktop centered... We basically have a blind spot regarding mobile devices" [xterm.js #5377](https://github.com/xtermjs/xterm.js/issues/5377)
- Same comment warns about the input path specifically: "parts of the key handling is very old and tricky code, that evolved over time from issue reports and cannot be tested in a straight forward way. I'd call it the ugly duck in xterm.js" [xterm.js #5377](https://github.com/xtermjs/xterm.js/issues/5377)
- Maintainer Tyriar: "For touch support, using the default DOM renderer and/or `screenReaderMode` would be a requirement to get touch working." And on input: "you basically need to implement your own keyboard or at least some bar with all the relevant characters. I don't know if you can give a hint to the browser to disable how mobile IMEs collect characters and instead have them send each keystroke immediately. This is out of scope for this library." [xterm.js #5377](https://github.com/xtermjs/xterm.js/issues/5377)
- A downstream implementer reports success rolling their own: "I implemented all the touch interactions myself. Selection is handled through custom selection handles and by calculating touch coordinates. I also created custom selection handles and context menus, which makes the experience much more usable... There are still some quirks, especially due to mobile virtual keyboards" [xterm.js #5377](https://github.com/xtermjs/xterm.js/issues/5377)
- Reported regression: "scrolling appears to have gotten worse for mobile on v6.0.0" and "Dragging the scrollbar always detaches from the finger's position. I hope we can support scrolling the page by sliding up and down with two fingers instead." [xterm.js #5377](https://github.com/xtermjs/xterm.js/issues/5377)
- Another reporter: "~50% of drags don't send any scroll events... after scrolling 1 or 2 lines it 'detaches' and stops sending events" [xterm.js #5377](https://github.com/xtermjs/xterm.js/issues/5377)
- **IME workaround reported to work**: "regarding the IME thing keyboards do on mobile, I've swapped the input element for a password field and it successfully fixes it for gboard for me so far, but of course this is kind of a hack and shows my password manager button on the suggestion bar" [xterm.js #5377](https://github.com/xtermjs/xterm.js/issues/5377)
- Older workarounds from the long-running mobile issue: `terminal.textarea?.setAttribute("enterkeyhint", "send")` improves Enter handling on Android [xterm.js #1101](https://github.com/xtermjs/xterm.js/issues/1101); iOS hardware-keyboard arrows only fire `keydown` when focus is on `document.body`, not the hidden textarea, requiring a refocus hack [xterm.js #1101](https://github.com/xtermjs/xterm.js/issues/1101)
- Android soft-keyboard behavior varies by IME: "For example SwiftKey, it looks that on every type it just pastes the symbol to the current input field. And how do you delete? It removes everything from the current input, and paste a new string with the removed last char." [xterm.js #1101](https://github.com/xtermjs/xterm.js/issues/1101)
- Confirmed that a textarea is required at all: hterm avoids one and consequently "the keyboard doesn't show up on iOS with hterm" [xterm.js #1101](https://github.com/xtermjs/xterm.js/issues/1101)

## Termux extra-keys: config format and long-press behavior

- Config lives in `~/.termux/termux.properties`, is a Java `.properties` file loaded via `java.util.Properties.load()`, reloaded with `termux-reload-settings` [termux.properties](https://github.com/termux/termux-tools/blob/master/termux.properties)
- Default: `extra-keys = [[ESC, TAB, CTRL, ALT, {key: '-', popup: '|'}, DOWN, UP]]`. Value is an array of rows; each entry is a string, a named key, or an object [termux.properties](https://github.com/termux/termux-tools/blob/master/termux.properties)
- **Long-press/swipe-up popup** is the second-function mechanism, documented as "Configuration with additional popup keys (swipe up from an extra key)". Examples:
  ```
  {key: ESC, popup: {macro: "CTRL f d", display: "tmux exit"}}
  {key: LEFT, popup: HOME}
  {key: UP, popup: PGUP}
  {macro: "ALT j", display: A-j, popup: {macro: "ALT g", display: A-g}}
  {key: KEYBOARD, popup: {macro: "CTRL d", display: exit}}
  {key: ESC, popup: {macro: ":q\n", display: "QuickExit"}}
  ```
  So a popup can be a plain key, a macro (multi-keystroke sequence), or literal text, each with its own `display` label [termux.properties](https://github.com/termux/termux-tools/blob/master/termux.properties)
- Valid named keys: CTRL, ALT, FN, ESC (the four "special keys"), TAB, HOME, END, PGUP, PGDN, INS, DEL, BKSP, UP, LEFT, RIGHT, DOWN, ENTER, BACKSLASH, QUOTE, APOSTROPHE [Mobile Coding Hub — Extra Keys](https://mobile-coding-hub.github.io/termux/customisation/extra_keys/)
- **Documented bug**: "Each of the four 'special keys'... should only be listed at most ONCE in the extra-keys definition i.e. do NOT have more than one CTRL key. Having more than one instance of any 'special key' will result in a bug whereby those keys do not function correctly." [Mobile Coding Hub — Extra Keys](https://mobile-coding-hub.github.io/termux/customisation/extra_keys/)
- Related properties: `extra-keys-style` (default / arrows-only / arrows-all / all / none), `extra-keys-text-all-caps`, `soft-keyboard-toggle-behaviour`, `hide-soft-keyboard-on-startup`, `back-key=escape` (map Android back button to Esc), `terminal-margin-horizontal`/`vertical`, `terminal-transcript-rows` (max 50000) [termux.properties](https://github.com/termux/termux-tools/blob/master/termux.properties)
- Termux also has **keyboard workaround flags** for real mobile bugs: `enforce-char-based-input = true` ("Letters might not appear until enter is pressed on Samsung devices") and `ctrl-space-workaround = true` [termux.properties](https://github.com/termux/termux-tools/blob/master/termux.properties)
- **Volume keys as modifiers** is Termux's answer to missing physical modifiers: Volume-Down acts as Ctrl (VolDn+L = Ctrl+L); Volume-Up produces Esc (VolUp+E), Tab (+T), F1-F10 (+1..+0), arrows (+W/A/S/D), PgUp/PgDn (+P/+N), `|` (+L), `~` (+H), `_` (+U), Alt+B/Alt+F for readline word motion, and toggles the extra-keys row (+Q or +K) [Mobile Coding Hub — Extra Keys](https://mobile-coding-hub.github.io/termux/customisation/extra_keys/), [Termux Touch Keyboard wiki mirror](https://gist.github.com/eggplants/ab749bf56cd9d02cc04a3cf7ba99d567)
- Termux's terminal long-press opens a context menu (Select/Paste/Reset/Hangup/Style); pinch in/out changes font size; swipe from left edge opens the session drawer [Practicalli Neovim — Using Termux](https://practical.li/neovim/termux/using-termux/)
- UNCERTAIN: `extra-keys` multiple-popup-keys-per-key is requested but reportedly unsupported — "When I try to add multiple popup keys with an array in termux.properties, the extra keys keyboard is reset to its original configuration" [termux-app #2624](https://github.com/termux/termux-app/issues/2624)

## Full-screen TUIs on phones — reported experience

- A 2026 field report claims tmux, vim, htop, lazygit, and Claude Code "rendered cleanly in the alternate screen, redrew correctly after orientation changes, and survived two backgroundings each" on a Pixel 8 and iPhone 14, and that "Where the experience broke down was always the keyboard layer, not the TUI layer: glass keyboards do not give you ESC, CTRL, ALT, or arrow keys for free" [Cosyra — TUI Apps on Phone](https://cosyra.com/guides/tui-apps-on-phone.html)
- Same source lists the requirements it considers necessary: alternate screen support, accurate redraws, raw keyboard input, modifier keys, paste behavior "that does not corrupt commands", and long-lived process state [Cosyra — TUI Apps on Phone](https://cosyra.com/guides/tui-apps-on-phone.html)
- Its argument for why agents fit phones: "the phone workflow is prompt, wait, inspect, approve, and redirect. That maps to a terminal better than it maps to a desktop IDE compressed into mobile Safari. A TUI agent takes the whole viewport, streams output line by line, asks permission in place" [Cosyra — TUI Apps on Phone](https://cosyra.com/guides/tui-apps-on-phone.html)
- UNCERTAIN: this is vendor marketing for a paid product (Cosyra), and the device testing is self-reported with no methodology. Treat the "rendered cleanly" claim as a vendor assertion [Cosyra — TUI Apps on Phone](https://cosyra.com/guides/tui-apps-on-phone.html)
- Textual runs on Android via Termux and has since at least 2022, with a demo video; multiple users report daily use [textual #583](https://github.com/Textualize/textual/discussions/583)
- Reported Textual-on-Termux problems: "clicking on URLs seems to not function for termux" (Oct 2025), and install failures related to tree-sitter packages missing from Termux [textual #583](https://github.com/Textualize/textual/discussions/583), [textual #5644](https://github.com/Textualize/textual/issues/5644)
- Rocket Pool community request for a phone-sized TUI: "Would it be possible to adjust the TUI so that we can access it everywhere on the globe via a smart phone sized display?" [Rocket Pool DAO forum](https://dao.rocketpool.net/t/adjust-terminal-user-interface-size-to-make-it-suitable-for-smartphones/2861)
- Sxmo is a text-centric mobile UI whose terminal uses volume-down tap or a bottom swipe to toggle the virtual keyboard [LWN — Sxmo](https://lwn.net/Articles/981320/)

## Explicit "touch-friendly TUI" prior art

- `ThyFriendlyFox/tui-touchscreen-demo` is a Textual app "designed to be touchscreen-friendly" with custom `TouchableButton`, `TouchableInput`, `TouchableSelect`, `TouchableDataTable` widgets. Its stated touch design principles: "Large Click Targets: Buttons and interactive elements have adequate padding", "Visual Feedback: Clear borders and color coding", "Touch-Friendly Spacing: Adequate margins between elements", "Responsive Layout" [tui-touchscreen-demo](https://github.com/ThyFriendlyFox/tui-touchscreen-demo)
- Its "Future Enhancements" list confirms what is *not* available today: "Gesture Support: Swipe gestures for navigation", "Multi-touch: Support for multiple simultaneous touches", "Touch Calibration" [tui-touchscreen-demo](https://github.com/ThyFriendlyFox/tui-touchscreen-demo)
- `inventree-tui` is a TUI "built for the Raspberry Pi 1 B+ kiosk (touchscreen + USB keyboard)" and reads touch from a raw Linux input device rather than the terminal: `INV_TUI_TOUCH=/dev/input/event2` to pin a device, requiring the user be in the `input` group — i.e. bypassing the terminal mouse protocol entirely [inventree-tui](https://github.com/AndrewYatzkan/inventree-tui)
- Terminal Click (a commercial terminal, June 2026 devlog) shipped TUI mouse events as a headline feature: "Terminal Click now allows TUIs to receive a user's mouse inputs... Mouse events also work over the network! If you're using `vim`, make sure you run the command `:set mouse=a` first." [Terminal Click devlog](https://terminal.click/posts/2026/06/tui-mouse-events)

## TUIs rendered in a browser (adjacent architecture)

- **Ratzilla** compiles ratatui to WASM with a `DomBackend` (also a `CanvasBackend` and a WebGL2 backend), rendering a TUI into a `<pre>` element. Its template `index.html` uses `<meta name="viewport" content="width=device-width, initial-scale=1.0, user-scalable=no">` and `height: 100vh` [Ratzilla README](https://github.com/orhun/ratzilla)
- Ratzilla's event API is `terminal.on_key_event(...)` and `terminal.draw_web(...)`; no touch or pointer events are documented in the README [Ratzilla README](https://github.com/orhun/ratzilla)
- **textual-web** / **textual-serve** run Textual apps in a browser; Textual has published a "Towards Textual Web Applications" post [textual-web](https://github.com/textualize/textual-web), [Towards Textual Web Applications](https://textual.textualize.io/blog/2024/09/08/towards-textual-web-applications/)
- **OpenTUI** claims to power OpenCode in production, "an extensible core with a focus on correctness, stability, and high performance" with component-based architecture and flexible layout [OpenTUI](https://opentui.com/)
